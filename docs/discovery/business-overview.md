## 参与者与业务边界

| 参与者 | 业务职责 / 当前边界 |
|---|---|
| 接入方业务系统 | 首期为一个模拟商城，提供普通业务订单并消费支付结果；商品、库存与履约仍属商城侧业务，不据此扩张为完整商城或多租户商户入驻项目。 |
| 付款人 | 业务流程中的间接外部参与者。当前不涉及真实付款人、真实收银页面或真实资金。 |
| Payment Hub | 接收统一支付请求、关联支付业务与渠道结果并向接入方交付结果。首期已确定仅查询，不接收渠道回调，也不主动通知接入方。 |
| Mock Provider / 未来支付渠道 | 作为逻辑上的外部支付能力提供者；此称谓不表示独立部署进程、微服务或特定技术结构。 |
| 开发者 | 兼任个人项目的演示、验证和排障角色；不因此要求建设运营管理后台。 |
| 财务 / 对账操作人员 | 可能参与未来账单与资金核对；不属于当前 Mock 闭环的必要参与者。 |

本文使用“接入方”指调用支付中台的业务系统，不自动等同于渠道登记的商户号，也不代表商户入驻、收单资质或资金管理功能。Payment Hub 不被预设为持牌收单、资金托管、清算或钱包系统；本文也不作法律或合规认证判断。

## 成熟支付平台的典型业务能力

下表对比 Stripe PaymentIntents 与微信支付 APIv3 普通商户文档。属于 **R** 的内容仅适用于所引平台和产品，不能直接作为 Payment Hub 的产品范围或对象模型。

| 能力 | 平台证据与差异 | 对本项目的业务含义 |
|---|---|---|
| 支付流程与结果确认 | Stripe PaymentIntent 表达支付流程，通常对应购物车、订单或客户会话，可包含多次支付尝试。[S1] 微信文档描述支付完成后的异步通知，并要求结合查询获取结果。[S6] | **A**：分清支付流程对象、单次支付尝试和一次技术请求/重试；不照搬 Stripe 的对象结构。 |
| 业务订单与渠道交易关联 | 微信文档区分商户系统内部订单号与微信支付侧订单号。[S6] Stripe PaymentIntent 是 Stripe 侧支付流程对象，并非本项目业务订单的同义词。[S1] | **A**：业务订单、平台支付订单、渠道交易各自有业务含义，通过关联识别，不混用标识。 |
| 查询与异步通知 | 微信说明支付结果通知可能重复、遗漏或延迟，应结合查询；Stripe要求集成方能应对事件延迟、重复及不保证顺序。[S3]、[S6] | **A**：同步响应、查询结果和异步事件是不同结果来源；结果确认要容忍异步和不确定性。 |
| 幂等和不确定请求 | Stripe支持相同幂等键安全重试，同一键不同参数会报错；网络断开不说明请求是否已执行。[S2]、[S4] | **A**：定义业务意图重复、冲突和技术重试的不同处理语义；Stripe的键规则和期限不是通用约定。 |
| 退款 | Stripe单次退款金额不能超过原支付剩余未退金额；可多次部分退款，累计退款不能超过原支付金额。[S5] 此为 Stripe 文档事实，不证明所有渠道退款都支持相同行为。 | **A**：退款应有自己的业务请求及原支付关联；何时纳入、退款范围和渠道差异后续确定。 |
| 交易账单 / 交易对账 | 微信交易账单包含支付与退款明细；账单生成后的退款状态不会更新，最新状态需另查。[S7] | **A**：对账需区分账单快照与实时查询结果，识别差异；单笔查单不是账单交易对账。 |
| 资金结算 / payout 核对 | Stripe payout reconciliation 按打款批次核对关联余额交易；它不是对单笔支付状态的确认。[S8] | **A**：资金可用、渠道结算或打款核对与交易对账相关但不同；不纳入首期。 |
| 两层通知边界 | 微信渠道通知发给与渠道集成的商户系统。[S6] 聚合平台若向自己的接入方发通知，是另一业务边界，并非渠道回调的别名。 | **A**：区分“渠道→中台”与“中台→接入方”。收到通知并应答，不应自动声称业务结果已可靠交付或处理完成。 |

**适用限制：**所列平台能力用于识别常见业务问题，不意味着 Stripe 全部产品范围、Connect、钱包、订阅或其对象模型应被照搬；微信 JSAPI 也只是普通商户的一种支付场景。本文没有研究支付宝、全部银行卡产品或监管要求。单一平台支持某功能，不足以证明该功能是首期必需。

## 主场景与依赖关系

### 已确认首期的支付结果闭环

接入方提交支付意图 → Payment Hub 记录并关联业务订单 → 单一 Mock 返回模拟结果 → Payment Hub 提供查询结果 → 接入方据结果决定后续业务处理。

超时或结果未知时，先查询 Mock 核实，不因请求超时而盲目创建新的支付效果；若查询仍未知，应保留未知并可追踪，不伪装成失败。重复、并发、冲突请求是贯穿该流程的横切业务情境，不是另一个渠道或独立产品模块。

### 候选主场景与依赖

| 场景 | 参与者 / 目标 | 业务依赖 | 建议阶段 |
|---|---|---|---|
| 发起支付 | 模拟商城提交一次性付款意图，Payment Hub 获得模拟渠道结果。 | 业务订单关联、CNY 整数分、单 Mock。 | 首期已确认。 |
| 查询结果 / 未知核实 | 接入方查询；Payment Hub 核实或呈现尚不确定的结果。 | 支付订单与 Mock 结果可关联；原支付结果未知时，核实失败仍保留未知；已有已确认结果时，本次查询失败不得使其降级，仅记录查询失败。 | 首期已确认。 |
| 重复和冲突意图 | 相同请求返回已有结果；金额或币种冲突明确拒绝；失败后不重付。 | 接入方标识与商城业务订单号共同识别意图；不新增支付尝试或自动换渠道。 | 首期横切验收。 |
| 重启后查询与复用 | 重启后仍能查询已登记订单，同一意图仍复用原订单。 | 已登记订单及其确认或未知结果须保留；具体实现留待技术设计。 | 首期已确认。 |
| 渠道回调 | 渠道向 Payment Hub 异步报告结果。 | 支付订单/渠道交易关联，来源、完整性和订单匹配核验。 | 后续候选。 |
| 中台商户通知 | Payment Hub 向接入方交付支付结果。 | 可信结果及接收方的重复、延迟处理语义。 | 后续候选，不是渠道回调。 |
| 退款 | 接入方对已确认支付提出退款业务请求。 | 原支付关联、退款额度规则及目标渠道退款行为。 | 后续候选；不依赖先做多渠道。 |
| 交易对账 | 业务人员核对内部记录与渠道交易账单。 | 可关联的支付记录、可用账单和差异处理约定。 | 后续候选；可先核支付，无需等待退款。 |

### 未来能力的业务依赖

- 渠道异步回调依赖支付订单与渠道交易的关联，以及对通知来源、完整性和订单匹配的核验。
- 商户通知依赖可信的支付结果与明确的接收方交付语义；不是首期查询的前置条件。
- 退款依赖已确认的原支付及明确的退款额度、重复请求和渠道规则；不要求先建设多渠道。
- 交易对账依赖可关联的内部记录、可获取的渠道账单和差异处置方式；可先对已支持的支付交易核对，不强制等待退款功能。
- 资金结算核对关注资金批次与结算/打款，不是完成单笔支付查询或交易账单比对的前置条件。

## 已确认的首期 Mock 闭环（F）

以一个模拟商城、一个 Mock Provider、单币种 CNY 为边界：登记平台支付订单并关联商城普通业务订单；发起一次性模拟支付；仅通过查询获取结果；遇到未知结果时向 Mock 核实或继续保留未知。金额采用整数“分”，有效范围为 1 至 1,000,000 分，两端包含，即 0.01 至 10,000 元；这是演示业务边界，不是渠道或监管限额。

首期以“接入方标识＋商城业务订单号”唯一识别业务支付意图。同一意图复用已有支付订单，相同请求返回已有结果；金额或币种冲突时明确拒绝，不覆盖已有记录。首期不创建多次支付尝试、不自动切换渠道，也不支持明确失败后的重新支付。

服务重启后，已登记订单仍须可查询，同一意图仍复用原订单，不得因重启产生第二次支付。已有确认结果保留；原结果未知时不能因重启推定成功或失败，后续仍可核实或保持未知。此要求不预先指定存储技术。

上述范围、三项关键契约与正式需求规格已由用户确认。查询驱动仅是首期演示范围，不代表真实支付流程可以省略适用的异步通知。

### 首期非目标

- 真实支付渠道、真实资金、真实付款人收银页。
- 完整商户入驻、多租户运营后台、分账或资金托管。
- 渠道回调入口、中台商户通知及其生产级投递能力。
- 退款、自动多渠道路由/故障切换、渠道优选。
- 渠道账单下载与交易对账、资金结算核对、钱包能力。

### 业务验收要点（具体场景见正式规格）

- 模拟成功和模拟失败均可由接入方查询到与请求相符的结果。
- 1 分与 1,000,000 分在其他条件有效时可受理；0 分、负数、1,000,001 分、非整数分或非 CNY 币种被明确拒绝，不产生支付效果。
- 同一业务意图重复或并发提交复用已有支付订单与结果，不产生重复业务效果；金额或币种冲突明确拒绝，不覆盖原记录。
- 已明确失败的同一业务意图再次提交时仍返回已有结果，不发起新的支付尝试，也不自动切换渠道。
- 模拟请求超时后，查询能够确认已成功的结果时不再次产生模拟支付效果。
- 原支付结果未知时，查询持续失败仍保留未知并能追踪；不以超时推定成功或确定失败。
- 已有已确认结果时，本次查询失败不得使其降级或覆盖该结果，仅记录查询失败。
- 冲突的终态信息不会静默覆盖已确认结果。
- 成功、失败及未知订单在服务重启后仍可按原意图查询或复用，不丢失已登记关联，也不产生重复支付效果。

以上是业务结果验收要点；精确场景与成功标准以正式需求规格为准，不预设存储机制、接口路径或技术实现。

## 后续迭代候选路径（非承诺）

1. 完成首期闭环后，按学习目标决定后续是否加入渠道异步结果与中台对接入方的通知。
2. 再选择第二个 Mock 渠道，或实现一次全额退款；二者为可独立讨论的学习切片，不互为先决条件。
3. 交易账单对账可先覆盖已支持的支付；退款纳入后再决定是否同时核对退款账单记录。
4. 真实资金接入须单独重新评估并取得明确授权，不是 Mock 成功后的自动下一步。

结果未知时自动切换渠道有产生重复支付的风险，不能把自动故障切换当作默认扩展捷径。

| C3 | 服务重启后仍保留已登记订单的查询及原意图复用保障。 | 保留已确认或未知结果，不因重启重复支付；具体存储方案留到技术设计。 |

## 结语

Q1–Q5 的首期范围及 C1–C3 的关键业务契约已确认，并写入[正式需求规格](../../specs/001-mock-payment/spec.md)。需求基线已于 2026-11-05 审阅确认，后续技术设计以此为依据；本阶段不包含代码实现，也不一次性设计全部未来能力。
