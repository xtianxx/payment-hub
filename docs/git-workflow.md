# Git 协作与交付规范

本规范适用于 Payment Hub 的人工与 AI 协作，由项目负责人于2026-11-14确认采用。目标是小步交付、中文可读、验证可追溯、操作有授权。

本规范细化[项目宪章](../.specify/memory/constitution.md)已有的最小完整成果、风险验证及人类负责原则，不修改宪章。历史开发记录用于追溯，不替代本规范；发现冲突时先报告并确认，不静默绕过。

## 1. 分支

- `main`保持可交付，禁止直接在main开发、直接推送或强推；常规变更必须通过功能分支与PR。
- 新任务从最新远端main创建分支。先核对工作区和远端基线，已有未提交改动不得擅自丢弃、覆盖或混入新任务。
- 分支名称使用小写英文、数字和连字符，格式为`类型/简短主题`：

| 前缀 | 用途 | 示例 |
|---|---|---|
| `feat/` | 新功能 | `feat/payment-query` |
| `fix/` | 缺陷修复 | `fix/release-bootstrap` |
| `ci/` | 工作流与自动化检查 | `ci/daily-vulnerability-scan` |
| `docs/` | 文档与规范 | `docs/git-workflow-policy` |
| `refactor/` | 不改变行为的重构 | `refactor/payment-validation` |
| `chore/` | 仓库维护 | `chore/toolchain-metadata` |

- 一个分支聚焦一个目标。目标内可拆分多个最小完整提交；无关问题另建分支或明确扩展范围。
- 不要求main上的每个提交都已正式发布；可交付不等于已上传镜像或已部署。

## 2. 提交

提交标题采用`类型(可选范围): 中文描述`，类型及代码标识保留英文，标题和正文以中文为主。例如：

```text
fix(release): 补充首次发布初始化流程

说明修改原因、关键行为与边界，并记录实际验证及未验证项。
```

- 常用类型：`feat`、`fix`、`ci`、`docs`、`refactor`、`test`、`chore`；按实际改动使用`build`、`perf`、`style`、`revert`，不为统一格式歪曲含义。
- 一个提交表达一个可说明、可验证、可回退的完整逻辑变更。不按文件数机械拆分，不拆散不可分割的实现、测试与必要文档。
- 提交前审查暂存差异、目标分支和文件清单，显式选择本次文件；不把全量暂存当作默认操作。
- 验证与风险匹配。纯文档检查链接、内容一致性和空白即可；代码或工作流变更运行对应回归，缺陷修复补充回归证据。
- 禁止提交真实密钥、token、Authorization、DSN、支付敏感信息、原始敏感日志、真实`.env`及临时构建产物。忽略规则不是安全审查的替代品。
- 正文或PR必须说明实际执行的命令、结果、未执行项和原因；不得将旧输入的绿灯、fake测试或推测包装成当前真实链路通过。
- 提交不等于推送授权。不得跳过提交钩子或校验；钩子失败先诊断，不默认使用绕过选项。

## 3. 历史整理与同步

- 未推送的提交可在项目负责人明确授权后整理或改写；改写前核对范围，保留可恢复的原引用，并核对最终文件内容。
- 已共享的提交默认不改写。确需整理功能分支时，须明确授权、确认无人依赖旧历史并保留恢复点；不得默认强推，更不能改写main。
- 远端分支推进后，不用强推覆盖他人提交；先核对差异，再选择适用的同步方式。
- 不擅自重置、清理或暂存他人的工作，不修改全局Git配置，不将凭据写入remote URL。

## 4. PR与合并

- PR默认以main为目标，标题、说明与最终合并提交以中文为主。
- PR说明至少包含：目的、范围、主要变更、验证命令与结果、风险、未验证事项及需要人工执行的步骤。
- 可先创建Draft PR获取CI反馈；Draft与普通PR都不代表已获合并授权。合并前须完成审查并转为可合并状态。
- 必须核对PR当前head SHA、目标分支及检查结果；新增修复提交后，旧SHA的绿灯不再作为合并依据。
- 当前两项必要检查为`CI gate`及`Paired image acceptance (linux/amd64)`；前者汇总基础、数据库和漏洞检查，后者独立覆盖镜像验收与交接预检。
- 合并前上述检查必须成功，其他适用检查不得失败、取消或仍在运行。PR所需检查的缺失、skipped或neutral不当作成功；定时扫描按设计跳过其他作业，不属于PR验收。
- 远端ruleset应配置上述必要检查。文档不代表服务端已强制执行；规则尚未配置时仍须人工或代理核对，不能利用保护缺口合并红灯。
- **统一采用压缩合并（Squash）**，保留功能分支中的合理提交拆分用于审查，在main形成一个完整交付记录。合并前复核最终中文标题、正文及当前head。
- 合并后确认PR状态、main合并提交和新一轮main检查；PR绿灯不替代合并后SHA的绿灯。
- 合并不默认删除分支。得到清理授权后，确认没有未合并、未推送或他人依赖的工作，再删除已完成分支；不得删除main。

## 5. 发布、标签与回退

- 提交、推送、创建PR、合并、发布、部署及版本标签是不同操作，授权不能自动跨越这些边界。
- 正式发布只走受控main工作流，仍须满足同SHA必要CI、包权限与人工确认等现有门禁；不得为“让流程通过”放宽隐私、内容身份或业务正确性检查。
- 每日漏洞扫描是额外安全观察，不替代push/main发布门禁，也不自动升级依赖、创建修复、发布或部署。
- 发布、部署、创建或移动远端版本标签均需对应授权；不得把合并成功表述为发布成功。
- 已合并问题优先用新修复PR或revert PR处理，不改写main历史。回退也需审查、验证与操作授权，不默认回滚数据库或已部署环境。
- 如有紧急处理需求，由项目负责人明确确认范围和风险，不默认免除关键检查。

## 6. AI操作授权

- 在已批准任务范围内，AI默认可本地修改、测试和审查；新建分支、整理历史、提交和外部写操作遵循当前明确授权。
- 未明确授权时，不提交、不推送、不创建PR、不合并；不强推、不跳过检查、不修改远端保护规则、不触发正式发布或部署。
- 用户已授权完整链路（例如“提交、提PR，全绿后合并”）时，可在该任务范围内连续完成，不重复询问已确定的步骤；不得扩展到无关任务或后续新任务。
- 授权链路中遇到失败、冲突、权限不足、目标变化或真实人工审批时，先核对证据；需要改变安全边界、增加外部副作用或扩大范围时暂停并确认。
- 推送及创建PR可能自动触发CI，执行前说明这一影响；不得把它混同为手动正式发布授权。
- 有检查等待中时使用可恢复的后台等待机制，核对同一PR和SHA后接续处理；超时、空检查列表或“可合并”标志均不是全绿证据。

## 7. 规则维护与事实边界

- 修改本规范须由项目负责人明确确认，并与代理入口及相关说明同步；AI不得自行放宽授权或门禁。
- 本次只落地文档与代理引用，不安装提交钩子、不修改Git全局配置、不改变GitHub ruleset或仓库权限。
- 新规范适用于后续工作，不改写历史开发记录，也不追溯修改既有提交或自动恢复已暂停任务。
