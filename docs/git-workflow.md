# Git 协作与交付规范

本规范适用于 Payment Hub 的人工与 AI 协作，由项目负责人于2026-11-14确认采用。目标是小步交付、中文可读、验证可追溯、操作有授权。

本规范细化[项目宪章](../.specify/memory/constitution.md)已有的最小完整成果、风险验证及人类负责原则，不修改宪章。历史开发记录用于追溯，不替代本规范；发现冲突时先报告并确认，不静默绕过。

提交格式采用Conventional Commits 1.0.0，版本语义采用Semantic Versioning 2.0.0；分支、原子提交与PR管理参考Cabinet Office Digital Handbook。正文、提交描述、PR与发布说明以中文为主，保留类型、Scope、Footer令牌和代码标识。Cabinet Office的组织专属要求不自动适用：本项目保留下述分支命名及个人项目负责人审查机制，不引入其工单命名、多人审批、发布分支或许可制度。

## 1. 分支

- `main`保持可交付，禁止直接在main开发、直接推送或强推；常规变更必须通过功能分支与PR。
- 新任务从最新远端main创建分支。先核对工作区和远端基线，已有未提交改动不得擅自丢弃、覆盖或混入新任务。
- 常规分支名称使用小写英文、数字和连字符，格式为`类型/简短主题`：

| 前缀 | 用途 | 示例 |
|---|---|---|
| `feat/` | 新功能 | `feat/payment-query` |
| `fix/` | 缺陷修复 | `fix/release-bootstrap` |
| `ci/` | 工作流与自动化检查 | `ci/daily-vulnerability-scan` |
| `docs/` | 文档与规范 | `docs/git-workflow-policy` |
| `refactor/` | 不改变行为的重构 | `refactor/payment-validation` |
| `chore/` | 仓库维护 | `chore/toolchain-metadata` |

- Spec Kit生成的规格任务分支允许使用`NNN-简短主题`（如`006-payment-query`），以兼容现有编号与规格目录关联机制；此例外仅适用于Spec Kit规格任务，其他分支仍使用上述类型前缀，不为符合格式将文档、修复等任务一律标为`feat/`。
- 一个分支聚焦一个目标。目标内可拆分多个最小完整提交；无关问题另建分支或明确扩展范围。
- 分支保持短生命周期，大任务按可独立验证的完整成果拆成小PR，不以长期分支积攒无关改动。
- 不要求main上的每个提交都已正式发布；可交付不等于已上传镜像或已部署。

## 2. 提交

提交采用以下结构，Scope、Body和Footer可选；破坏性变更标记规则见下文：

```text
<type>[(scope)][!]: <中文描述>

<Body：变更原因、关键行为及必要验证说明>

<Footer：关联事项或破坏性变更说明>
```

方括号表示可选项，不写入实际提交；标题使用英文半角冒号与一个空格。类型统一小写；Scope描述受影响的模块，如`payment`、`release`、`ci`，不以工单号代替模块。标题简要说明“做了什么”，正文重点解释“为什么”。标题以整行不超过50个Unicode字符为目标，不以句号结尾；正文自然分段，普通文字建议在72个字符内换行，命令、URL和代码标识不强行截断。这是适配中文的项目约定，不是Conventional Commits强制的行宽。例如：

```text
fix(release): 补充首次发布初始化流程

说明修改原因、关键行为与边界，并记录实际验证及未验证项。
```

- 常用类型：`feat`、`fix`、`ci`、`docs`、`refactor`、`test`、`chore`；按实际改动使用`build`、`perf`、`style`、`revert`，不为统一格式歪曲含义。
- 新功能使用`feat`，缺陷修复使用`fix`；其他类型是允许的扩展，不构成Conventional Commits的强制类型清单，也不单独决定版本递增。
- Body与标题之间、Footer与前文之间空一行。Footer使用`令牌: 值`或`令牌 #值`，例如`Refs: #12`；令牌中的空格用连字符代替，`BREAKING CHANGE`除外。不虚构关联事项、审查人或验证结果。
- 破坏性变更必须在冒号前用`!`标记（如`feat(api)!: 调整支付响应字段`），或使用大写脚注`BREAKING CHANGE: 中文说明`；`BREAKING-CHANGE`是等价令牌。仅使用`!`时，标题须说明不兼容变化；建议在正文或脚注补充影响与迁移方式。例如（仅演示格式，不代表已批准业务变更）：

  ```text
  feat(api)!: 将支付响应状态字段改为payment_status

  统一字段命名，调用方需更新响应解析逻辑。

  BREAKING CHANGE: 移除旧status字段，调用方须改用payment_status
  ```

- 一个提交表达一个可说明、可验证、可回退的完整逻辑变更。不按文件数机械拆分，不拆散不可分割的实现、测试与必要文档。
- 提交前审查暂存差异、目标分支和文件清单，显式选择本次文件；不把全量暂存当作默认操作。
- Spec Kit自动提交保持禁用：`.specify/extensions/git/git-config.yml`中的`auto_commit.default`及各事件的`enabled`均须为`false`。钩子注册启用不等于自动提交启用；不得直接开启现有会执行`git add .`并使用固定消息的自动提交。未来启用须先取得提交授权，改为显式审查的文件集合与合规中文提交说明，并验证不会混入已有改动。
- 验证与风险匹配。纯文档检查链接、内容一致性和空白即可；代码或工作流变更运行对应回归，缺陷修复补充回归证据。
- 禁止提交真实密钥、token、Authorization、DSN、支付敏感信息、原始敏感日志、真实`.env`及临时构建产物。忽略规则不是安全审查的替代品。
- 正文或PR必须说明实际执行的命令、结果、未执行项和原因；不得将旧输入的绿灯、fake测试或推测包装成当前真实链路通过。
- 提交不等于推送授权。不得跳过提交钩子或校验；钩子失败先诊断，不默认使用绕过选项。

## 3. 历史整理与同步

- 未推送的提交可在项目负责人明确授权后整理或改写；改写前核对范围，保留可恢复的原引用，并核对最终文件内容。
- 已共享的提交默认不改写。确需整理功能分支时，须明确授权、确认无人依赖旧历史并保留恢复点；不得默认强推，更不能改写main。
- 远端分支推进后，不用强推覆盖他人提交；先核对差异，再选择适用的同步方式。
- 已共享功能分支同步main时优先使用merge以保留历史；rebase属于历史改写，仍须遵循上述授权与恢复要求，不因参考外部实践而自动获得强推授权。
- 不擅自重置、清理或暂存他人的工作，不修改全局Git配置，不将凭据写入remote URL。

## 4. PR与合并

- PR默认以main为目标，标题、说明与最终合并提交以中文为主。
- PR说明至少包含：目的、范围、主要变更、验证命令与结果、风险、未验证事项及需要人工执行的步骤。
- 可先创建Draft PR获取CI反馈；Draft与普通PR都不代表已获合并授权。合并前须完成审查并转为可合并状态。
- 审查覆盖目的与范围、业务契约、可读性、兼容性、依赖必要性、失败路径测试及文档和部署影响。阻塞意见必须逐条修复或以证据说明不适用，不能把机器人标签当作事实，也不能未核查就批量标记解决。
- 必须记录并核对PR当前head SHA、目标分支、已验证的main基线SHA及对应检查结果；新增修复提交后，旧head SHA的绿灯不再作为合并依据。main推进后必须针对最新基线重新验证，不能只重读旧检查的成功状态。
- 当前两项必要检查为`CI gate`及`Paired image acceptance (linux/amd64)`；前者汇总基础、数据库和漏洞检查，后者独立覆盖镜像验收与交接预检。
- 合并前上述检查必须成功，其他适用检查不得失败、取消或仍在运行。PR所需检查的缺失、skipped或neutral不当作成功；定时扫描按设计跳过其他作业，不属于PR验收。
- 远端ruleset必须将上述两项设为必需状态检查，并启用严格最新基线要求（Require branches to be up to date before merging），不得绕过。文档不代表服务端已强制执行；若缺少这些保护，应暂停合并并报告，由项目负责人授权配置，不能仅靠人工复核替代服务端的合并时校验。本规范不自动授权修改远端设置。
- **统一采用压缩合并（Squash）**，保留功能分支中的合理提交拆分用于审查，在main形成一个完整交付记录。合并前复核最终中文标题与正文；合并动作必须绑定已验证的head SHA，例如使用`gh pr merge <PR> --squash --match-head-commit <已验证的head-SHA>`（中文标题、正文另行明确提供）。SHA不匹配时停止，重新审查和验证，不自动改用新head重试；不得使用绕过保护的选项。
- head SHA条件仅防止PR分支竞态，不锁定main基线；必须同时满足上述严格必需检查。若将来采用merge queue替代严格基线模式，须另行确认范围、为必需检查补齐`merge_group`触发并验证，不把尚未配置的队列当作已有保障。
- 合并后确认PR状态、main合并提交和新一轮main检查；PR绿灯不替代合并后SHA的绿灯。
- 合并不默认删除分支。得到清理授权后，确认没有未合并、未推送或他人依赖的工作，再删除已完成分支；不得删除main。

## 5. 发布、标签与回退

- 正式版本采用`MAJOR.MINOR.PATCH`，数字无前导零；使用前须明确公共API及兼容性边界。对已稳定的`1.0.0`及以后版本，不兼容API变更升MAJOR，兼容新增或公共API弃用升MINOR，兼容缺陷修复升PATCH；升MAJOR时MINOR/PATCH归零，升MINOR时PATCH归零。
- `0.y.z`表示初始开发、API尚不稳定，SemVer不强制其破坏性变更升MAJOR；仍须标记破坏性变更并说明迁移影响，具体版本在获得发布授权后依据兼容性评估确认，不因提交类型自动发布。
- 先行版本如`1.0.0-rc.1`低于对应正式版本；构建元数据如`+build.1`不参与优先级比较。`v1.2.3`可作为Git标签名，版本号本身是`1.2.3`。
- 已发布版本的内容不可修改，其对应版本标签不得移动；修正须发布新版本。镜像的可变查找标签不等同于SemVer版本标签，交付身份仍遵循现有digest核验要求。影响接入方的发布须提供中文发布说明和变更记录，说明新增、修复、弃用、破坏性变更及迁移方式；本次不新增发布流程或自动版本工具。
- 提交、推送、创建PR、合并、发布、部署及版本标签是不同操作，授权不能自动跨越这些边界。
- 正式发布只走受控main工作流，仍须满足同SHA必要CI、包权限与人工确认等现有门禁；不得为“让流程通过”放宽隐私、内容身份或业务正确性检查。
- 每日漏洞扫描是额外安全观察，不替代push/main发布门禁，也不自动升级依赖、创建修复、发布或部署。
- 发布、部署、创建或移动远端版本标签均需对应授权；不得把合并成功表述为发布成功。
- 已合并问题优先用新修复PR或revert PR处理，不改写main历史。回退也需审查、验证与操作授权，不默认回滚数据库或已部署环境。
- 如有紧急处理需求，由项目负责人明确确认范围和风险，不默认免除关键检查。

## 6. AI操作授权

- 在已批准任务范围内，AI默认可本地修改、测试和审查；新建分支、整理历史、提交和外部写操作遵循当前明确授权。
- 未明确授权时，不提交、不推送、不创建PR、不合并；不强推、不跳过检查、不修改远端保护规则、不触发正式发布或部署。
- 用户已授权完整链路（例如“提交、提PR，全绿后合并”）时，可在该任务范围内连续完成，不重复询问已确定的步骤；不得扩展到无关任务或后续新任务。
- 授权链路中遇到失败、冲突、权限不足、目标变化或真实人工审批时，先核对证据；需要改变安全边界、增加外部副作用或扩大范围时暂停并确认。
- 推送及创建PR可能自动触发CI，执行前说明这一影响；不得把它混同为手动正式发布授权。
- 有检查等待中时使用可恢复的后台等待机制，核对同一PR和SHA后接续处理；超时、空检查列表或“可合并”标志均不是全绿证据。

## 7. 规则维护与事实边界

- 修改本规范须由项目负责人明确确认，并与代理入口及相关说明同步；AI不得自行放宽授权或门禁。
- 本次只落地文档与代理引用，不安装提交钩子、不修改Git全局配置、不改变GitHub ruleset或仓库权限。
- 新规范适用于后续工作，不改写历史开发记录，也不追溯修改既有提交或自动恢复已暂停任务。
