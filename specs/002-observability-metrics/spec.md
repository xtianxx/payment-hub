# Feature Specification: 本地压测期间的支付服务指标采集与回看

**Feature Branch**: `002-observability-metrics`

**Created**: 2026-11-25

**Status**: Draft

**Input**: User description: "在本地负载测试期间，通过应用和数据库的指标端点采集 HTTP、Go 运行时、pgxpool 与 PostgreSQL 指标，由本地 Prometheus 抓取、Grafana 展示，用于解释压测结果；不改变支付业务契约，不建设常驻监控平台，不对外暴露。"

## Clarifications

### Session 2026-11-25

- Q: 这套指标的使用范围是什么？ → A: 仅用于本地压测期间的结果归因，不做常驻监控平台、不部署公网、不配置告警；压测结束后按保存的数据回看。
- Q: 首批覆盖哪些数据源？ → A: 应用指标（HTTP、Go 运行时、pgxpool）与 PostgreSQL 统计；应用在宿主机运行，因此不采 cAdvisor 容器指标，首批也不采 `pg_stat_statements` 逐条 SQL 统计。
- Q: HTTP 状态码标签用什么粒度？ → A: 使用精确状态码，查询时再聚合为 4xx、5xx；接口的状态码集合有限。
- Q: 是否要求服务端 P95 不高于客户端 P95？ → A: 不设通过/失败硬阈值；只要求同一时间窗可对照，并给出 ±3ms 或 ±20% 的对照容差，超出时解释时间窗或桶边界。
- Q: 指标数据如何保存？ → A: 一次完整运行一个独立目录，记录 12 位 `run_id` 和每个测量阶段的 UTC 起止时间，与 k6 结果同目录留档；不共用同一个指标库。
- Q: PostgreSQL 监控账号如何提供？ → A: 监控密码由观察者通过本地 `0600` 密码文件提供；入口在每轮数据库初始化时用该密码创建只读角色。密码不写入仓库、迁移文件、容器环境变量、命令行、日志或摘要，只通过 stdin 和只读挂载传递。
- Q: 观测栈提前启动时，exporter 如何连接每轮新建的数据库？ → A: 基准改用固定的本机回环端口（默认 55432），入口检查 55432 和 9091 并持有运行锁；exporter 连固定端口并重试到数据库就绪，跨 5 轮不重启。
- Q: 压测中观测栈失效时如何处理？ → A: 压测继续，基准资格仍按 k6 与对账判定；运行记录标记“指标证据不完整”，该运行不用于指标验收。
- Q: “指标证据不完整”由谁判定并记录？ → A: 压测结束后由检查脚本按 5 个测量阶段窗口查询抓取状态、`pg_up` 和关键序列，把完整或不完整的结果写入运行证据目录的 `metrics-evidence.json`。
- Q: 证据目录和数据库卷如何处理？ → A: 不自动删除；观察者确认不再需要后，按文档命令清理该次运行的数据。
- Q: 观测栈的固定开销如何避免影响对比？ → A: 需要对比的两次运行保持相同观测栈配置；绝对数值只在同一配置下比较，不与未启用观测栈的历史数据直接比较。
- Q: 服务端请求耗时的起止点如何定义？ → A: 从请求进入 API 路由组（含鉴权）开始，到 handler 链返回结束；包含响应序列化和写入 ResponseWriter 的时间，不含 socket 刷新和网络传输。被拒绝的请求也计入；慢客户端造成的写阻塞属于已知限制。
- Q: 指标端点默认是否开启？ → A: 默认关闭；只有显式设置 `PAYMENT_HUB_METRICS_ADDR` 才开启；开启后地址非法或监听失败即启动失败。普通启动行为不变。
- Q: 固定端口冲突和并发运行如何处理？ → A: 基准入口检查 55432 和 9091，并持有排他运行锁；观测栈 Compose 负责 9090 和 9187，回看阶段负责 3000；任一端口被占用时由对应组件明确报错，不静默改用其他端口；同一时间只允许一个运行。
- Q: 指标证据“完整”的判定阈值是什么？ → A: 以 5 个测量阶段窗口分别判定：每个窗口内应用、exporter 的每次抓取都成功，数据库连接 `pg_up=1`，抓取次数不少于按 5 秒间隔计算的期望值，且关键序列全部存在；任一窗口失败即整体不完整。
- Q: 压测被中断时指标证据如何计算？ → A: 只判定实际完成的测量阶段；未运行的阶段记为缺失，窗口终点取实际结束时间，整体标记为不完整。
- Q: Grafana 在压测期间是否常开？ → A: 不常开。测量轮次只运行 Prometheus 抓取，Grafana 在压测后启动回看，避免观测栈抢占 CPU 影响基准。
- Q: 指标数据按什么粒度保存？ → A: 一次完整运行一个目录，内含该次运行的 5 个测量轮，共用一份指标数据；轮次通过时间窗区分，不重启 Prometheus。
- Q: 测量轮数是否调整？ → A: 本期把基准入口固定为 5 个测量轮；原 3 轮实测记录保留为历史，不与新协议直接比较。
- Q: 服务端 P95 用什么统计窗口？ → A: 同时提供整轮 P95 和滚动窗口 P95；整轮结果用于验收和与 k6 对照，滚动窗口用于观察轮内趋势。
- Q: 观测栈如何交付和启动？ → A: 仓库提供按需启动的 Compose 配置，包含固定版本的 Prometheus、Grafana 和 PostgreSQL exporter；用完即停，不做常驻服务。
- Q: 观测栈由谁起停、数据如何归档？ → A: 观察者手动起停；压测结束后把指标目录归档到该次运行的证据目录，与 k6 摘要放在一起。

### Session 2026-11-26

- Q: 观测栈容器如何访问宿主机上的应用和数据库？ → A: 观测栈使用 host 网络，Prometheus、exporter、Grafana 各自绑定 127.0.0.1；仅支持 Linux/WSL2 同一来宾，不支持 Docker Desktop。
- Q: 容器以什么身份运行、如何读取密码文件？ → A: Prometheus 和 exporter 以宿主 UID/GID 运行；密码文件以只读方式挂载到固定路径；文件权限由入口脚本检查，exporter 不自行校验权限。
- Q: 数据库停止和 exporter 停止如何区分？ → A: `up` 表示能否抓到 exporter，`pg_up` 表示 exporter 能否连数据库；数据库停止时 `up=1`、`pg_up=0`，exporter 停止时 `up=0`。
- Q: 如何保证同一时间只有一个运行？ → A: 基准入口在 preflight 获取排他文件锁并持有到运行结束；端口检查作为辅助。
- Q: 回看是否会修改归档？ → A: 回看前把归档复制到临时目录，Prometheus 只写副本；归档目录保持不变。
- Q: 监控密码如何避免进入日志？ → A: 通过 stdin 传给 `psql`，不使用带密码的命令行参数；日志和摘要只记录“创建监控角色”，不记录密码。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 压测时能看清服务端接口表现 (Priority: P1)

观察者在压测开始前按文档启动 Prometheus，应用由基准入口启动；压测中和结束后，能按提交支付、按支付 ID 查询、按业务订单号查询三个接口，分别看到服务端的请求速率、错误比例和耗时分布，并与 k6 的客户端数据放在同一时间窗对照。

**Why this priority**: 这是判断一轮压测是否异常、慢在服务端还是客户端的锚点；没有它，资源指标没有参照，整条采集链路也无法先跑通。

**Independent Test**: 只启动应用和 Prometheus，发送一组可控请求（正常、401、服务端错误、无流量），检查三个接口的计数、错误比例和 P95 是否符合预期。不依赖数据库和连接池指标。

**Acceptance Scenarios**:

1. **Given** 应用和 Prometheus 已启动，**When** 发送 N 次提交支付请求，**Then** 服务端计数增加 N，并与 k6 的请求数在同一时间窗内一致；差异只能来自时间窗边界。
2. **Given** 已产生 401 和一次服务端错误，**When** 查询错误比例，**Then** 4xx 与 5xx 分别计数、互不混淆；有请求但没有 5xx 时结果为 0，完全没有请求时显示无数据。
3. **Given** 没有请求，**When** 查询请求速率，**Then** 速率为 0；停止应用后 `up=0`，用 `up` 区分抓取失败，不把 0 当成服务正常。
4. **Given** 一轮压测结束，**When** 在同一时间窗对比服务端 P95 与客户端 P95，**Then** 两者可对照，服务端耗时包含响应写入但不含 socket 刷新和网络发送，401 等被拒请求也计入；P95 差异在 ±3ms 或 ±20% 以内，超出时给出时间窗或桶边界解释。
5. **Given** 任意请求已记录，**When** 查询指标序列，**Then** `/readyz` 和指标端点自身不出现在支付接口序列中，标签不包含订单号、支付 ID、请求 ID 或原始 URL。

---

### User Story 2 - 压测时能看清应用资源和连接池 (Priority: P1)

压测中如果接口耗时上升，观察者能同时看到 Go 运行时和连接池状态，判断是 GC、goroutine 堆积、CPU 吃紧，还是请求在等数据库连接；停压后能看到这些量是否回落。

**Why this priority**: 接口表现只能说明“变慢”，资源与连接池回答“为什么慢”；两者结合才能形成可解释的结论。

**Independent Test**: 只启动应用和 Prometheus，用基准档位压一轮，压测中和停压后分别查询；不需要 Grafana，也不需要 PostgreSQL exporter。

**Acceptance Scenarios**:

1. **Given** 正在压测，**When** 查询 goroutine 数、堆内存和进程 CPU，**Then** 这些值随流量上升，停压后能观察到回落趋势；不设固定阈值。
2. **Given** 正在压测，**When** 查询 GC 暂停分布，**Then** 能用 GC 次数速率和平均暂停时间判断压测期间是否明显变频繁；累计分位数只作参考。
3. **Given** 连接池上限固定为 16，**When** 分别处于“只用 4 个连接”和“打满 16 个并出现等待”两种状态，**Then** 使用中、空闲、上限三个值能区分这两种情况。
4. **Given** 请求曾等待连接，**When** 查询等待次数和累计等待时长，**Then** 可以算出平均等待；有获取且等待为 0 时结果为 0，没有获取时显示无数据。
5. **Given** 应用已重启，**When** 查询计数类指标，**Then** 查询方式能处理归零，不把归零当成负增长。
6. **Given** 查询任意连接池指标，**Then** 结果中不出现连接串、用户名或密码。

---

### User Story 3 - 压测时能看清 PostgreSQL 在做什么 (Priority: P1)

压测中接口变慢时，观察者能同时看到数据库的连接、事务、锁和缓存情况，判断是数据库整体在忙、在等锁，还是磁盘 I/O 跟不上；数据库指标与应用指标能在同一时间窗对照。

**Why this priority**: 应用侧连接池只能说明“应用怎么用数据库”，无法说明数据库内部是否在等锁或读磁盘；缺少这层会把数据库问题误判为应用问题。

**Independent Test**: 只启动 PostgreSQL、exporter 和 Prometheus，压一轮后查询；再单独停掉应用，确认数据库指标仍能抓取。

**Acceptance Scenarios**:

1. **Given** 正在压测，**When** 查询事务提交速率，**Then** 它随流量上升，停压后回落。
2. **Given** 数据库出现锁等待，**When** 查询锁等待数量，**Then** 该值大于 0；锁等待为 0 时，不把“事务多”误判为“锁冲突”。
3. **Given** 数据库开始读磁盘或排序溢出，**When** 查询缓存命中率、临时文件和检查点写入耗时，**Then** 三者能分别观察到。
4. **Given** 数据库已停止，**When** 查询抓取状态，**Then** `up{job="postgres"}=1` 且 `pg_up=0`；exporter 停止时 `up=0`；数据库空闲时 `up=1`、`pg_up=1` 但事务速率接近 0。这几种状态可以区分。
5. **Given** 查询数据库指标，**Then** 仓库中不出现监控密码，exporter 只在本机可访问，且指标标签不包含 `usename` 或 `application_name`。
6. **Given** 观测栈在压测前启动，**When** 5 个测量轮依次重建数据库，**Then** exporter 使用固定端口和同一监控密码持续抓取，不因轮次切换而重启。

### User Story 4 - 压测后用 Grafana 回看和分析 (Priority: P1)

每次运行的指标保存到独立目录；压测结束后，观察者用 Grafana 打开预置看板，在对应时间窗里查看接口、资源、连接池和数据库四类指标，不需要手工建面板或写查询。观测栈由观察者按文档手动启动和停止，压测结束后把指标目录归档到该次运行的证据目录。

**Why this priority**: 保存和可视化是这套能力的使用入口；没有它，数据只能靠临时查询，无法支撑事后分析。

**Independent Test**: 用一次运行已保存的数据目录启动 Prometheus 和 Grafana，打开看板，确认四类指标都有数据；再用另一次运行的数据启动一次，确认两次运行的数据不会混在一起。

**Acceptance Scenarios**:

1. **Given** 已按文档启动观测栈，**When** 打开 Grafana，**Then** 数据源和看板已存在，不需要手工配置。
2. **Given** 一轮压测已结束，**When** 选择该轮时间窗，**Then** 接口、Go 资源、连接池和 PostgreSQL 四类指标都有对应面板。
3. **Given** 某类指标没有数据，**When** 查看看板，**Then** 没有样本时面板显示无数据而不是 0；抓取失败时 `up=0` 且面板显示异常。
4. **Given** 应用和 exporter 都已停止，**When** 用保存的数据目录重新启动，**Then** 仍能查看该轮完整时间窗。
5. **Given** 两次运行分别保存，**When** 切换数据目录，**Then** 两次运行的数据不会混在一起；同一次运行内的 5 个测量轮通过时间窗区分，不需要切换数据源。
6. **Given** 一次运行已结束，**When** 按文档归档指标目录，**Then** 指标数据与 k6 摘要位于同一运行证据目录；证据的 `run_id` 取 `summary.json` 的 12 位 `run_id`，另记 `run_dir` 目录名。
7. **Given** Grafana 已启动，**When** 从其他机器访问，**Then** 请求被拒绝，只允许本机访问。
8. **Given** 某次运行在压测中丢失指标，**When** 压测后运行检查脚本，**Then** 按 5 个测量阶段分别记录，未通过的阶段列出缺失项，整体标记“指标证据不完整”，且该运行不用于指标验收。

### Edge Cases

- 应用重启后计数类指标归零，查询与对比方式不得把归零解释为负增长。
- 未匹配到路由的请求归入一个固定标签值，不能按任意路径生成新时间序列。
- 观测栈缺失或未启动时，应用仍能正常启动、接收请求和完成压测。
- 抓取失败、抓取成功但无请求、抓取成功且有请求三种状态必须可区分。
- 压测窗口只有 120 秒，抓取间隔必须保证至少得到可用的时间序列；瞬时尖峰用累计量回答，不靠提高抓取频率。
- 轮内短时抖动必须用滚动窗口观察，不能只用整轮 P95 掩盖。
- 大响应或慢客户端可能拉高服务端耗时，因为计时包含 handler 内的响应写入；这是已知限制，分析时需与 k6 客户端耗时一起看。
- 多次运行的数据按运行标识隔离；同一次运行内的测量轮按时间窗区分，不能相互覆盖。
- PostgreSQL 或 exporter 停止时，应用侧指标仍可抓取；应用停止时，数据库侧指标仍可抓取。
- 基准入口负责检查 55432 和 9091；观测栈负责 9090、9187、3000。对应组件发现端口被占用时必须拒绝启动，不得静默改用其他端口。
- 监控密码文件缺失或权限不是 `0600` 时，入口必须拒绝运行；exporter 通过只读挂载读取同一文件，不自行检查权限。
- 观测栈在压测中失效时，压测继续；压测后的检查脚本必须写入“指标证据不完整”，不得把有效的压测判为失败。
- 两次压测运行不得并发；后启动的一方必须因运行锁或端口占用拒绝运行。
- 压测被中断时，指标证据只判定实际完成的测量阶段；未运行的阶段记为缺失，整体标记不完整。
- 回看使用归档副本；归档目录不可写不影响回看。副本已被另一个 Prometheus 实例占用时，回看必须拒绝启动并明确报错。
- exporter 在运行但数据库停止时，`up=1`、`pg_up=0`；不能把这种情况当作 exporter 抓取失败。
- Prometheus 自身在窗口中间停止时，抓取次数会少于按间隔计算的期望值，证据必须标记不完整。
- Grafana 数据源或看板 provisioning 失败时，启动必须明确失败或在日志中报错，不能以空看板继续。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 应用 MUST 默认不启动指标监听；仅当显式设置非空 `PAYMENT_HUB_METRICS_ADDR` 时，才在仅本机可访问的独立端口暴露指标端点，地址 MUST 是字面回环 IP:port，拒绝 `0.0.0.0`、`::`、空 host 和非回环主机名；不复用业务端口，不经过接入方鉴权。开启后地址非法或监听失败 MUST 使应用启动失败。
- **FR-002**: 系统 MUST 记录三个业务接口的请求计数，按方法、路由模板和精确状态码区分。
- **FR-003**: 系统 MUST 记录三个业务接口的耗时直方图，并同时支持整轮 P95 与滚动窗口 P95；整轮 P95 用于验收和与 k6 对照，滚动窗口用于观察轮内趋势。服务端耗时 MUST 从请求进入 API 路由组（含鉴权）开始，到 handler 链返回结束；包含响应序列化和写入 ResponseWriter 的时间，不含 socket 刷新和网络传输；被拒绝的请求也计入。
- **FR-004**: 指标标签 MUST NOT 包含订单号、支付 ID、请求 ID、接入方标识或原始 URL；未匹配路由 MUST 归入固定值。
- **FR-005**: 系统 MUST 采集 goroutine 数、堆使用量、GC 暂停分布的累计分位数、次数与总时长、进程 CPU 和常驻内存。
- **FR-006**: 系统 MUST 采集连接池上限、总数、空闲、使用中、建立中、获取次数、无空闲等待次数、累计等待时长、取消次数，以及连接新建和销毁次数。
- **FR-007**: 系统 MUST 通过独立 exporter 采集 PostgreSQL 的连接、事务、锁、缓存、临时文件和检查点指标；exporter MUST 在压测前启动，连接基准固定的本机端口并重试到数据库就绪，跨测量轮不重启。
- **FR-008**: PostgreSQL 监控账号 MUST 只读；监控密码 MUST 由本地 `0600` 密码文件提供，并在基准启动前由入口检查权限；入口 MUST 在 preflight 读取一次并在本次 5 轮中复用同一密码，运行期间文件变化不得改变本次运行使用的密码；密码 MUST NOT 写入仓库、迁移文件、容器环境变量、命令行参数、日志或运行摘要，只能通过 stdin 和只读挂载传递；exporter 不负责权限自检。
- **FR-009**: 压测期间指标抓取间隔 MUST 为 5 秒；应用与数据库 MUST 使用独立的抓取目标。
- **FR-010**: 每次完整运行的指标数据 MUST 保存为一个独立目录，内含该次运行的 5 个测量轮并共用一份指标数据，按轮次和测量阶段时间窗区分；运行标识 MUST 使用 `summary.json` 的 12 位 `run_id`，证据目录名为 `<UTC 时间戳>-<run_id>`；MUST 记录每个测量阶段的 UTC 起止时间，并在压测结束后归档到该次运行的证据目录，与 k6 结果同目录留档。
- **FR-011**: 仓库 MUST 提供按需启动的 Compose 配置，包含固定版本的 Prometheus、Grafana 和 PostgreSQL exporter；观测栈 MUST 使用 host 网络并只绑定回环地址，要求 Linux/WSL2 同一来宾；MUST 预置 Grafana 数据源和单一看板，可指向归档副本启动回看。
- **FR-012**: 系统 MUST 将关键查询结果导出为 CSV 和 JSON，写入运行证据目录下的 `metrics-export/`；导出 MUST 记录所用时间窗和查询语句，成功退出码为 0，参数或 IO 错误为 2，Prometheus 不可达为 4。
- **FR-013**: 系统 MUST 提供中文文档，说明启动、验证、查询、清理和修改后的检查步骤。
- **FR-014**: 引入指标 MUST NOT 改变支付接口的响应内容、状态、幂等语义或默认构建配置。
- **FR-015**: 观测栈缺失时，应用 MUST 仍能正常启动和压测。
- **FR-016**: 测量轮次 MUST 只运行 Prometheus 抓取；Grafana MUST 在压测结束后启动，不作为测量轮次的一部分。
- **FR-017**: 观测栈 MUST 按需启动和停止，不作为常驻服务运行。
- **FR-018**: 基准入口 MUST 固定为 5 个测量轮，命令行参数、单元测试和文档同步更新；原 3 轮实测记录 MUST 标记为历史，不作为新协议的基线。
- **FR-019**: 基准的 PostgreSQL MUST 使用固定的本机回环端口（默认 55432）；入口 MUST 在启动前检查 55432 和 9091 的占用，并 MUST 获取 `<artifacts root>/.payment-hub-load.lock` 的排他锁直到运行结束；锁或端口冲突时 MUST 拒绝运行；入口 MUST 在每轮用同一监控密码创建只读账号。
- **FR-020**: 观测栈失效 MUST NOT 改变基准资格；压测结束后 MUST 由检查脚本按 5 个测量阶段窗口查询抓取状态和关键序列，将完整或不完整的结果写入运行证据目录；标记不完整的运行 MUST NOT 用于指标验收。
- **FR-021**: 指标证据标记 MUST 记录每个测量阶段的窗口、两个抓取目标的状态、`pg_up`、抓取次数与期望次数、以及缺失的关键序列；完整性判定 MUST 要求每个已完成阶段内两个目标的抓取次数不少于期望值、应用侧每次 `up=1`、数据库侧每次 `up=1` 且 `pg_up=1`，且关键序列全部存在；任一阶段失败或缺失即整体不完整。
- **FR-022**: 证据目录和数据库卷 MUST NOT 自动删除；观察者确认不再需要后，MUST 按文档中的命令清理该次运行的数据。
- **FR-023**: 需要对比的两次运行 MUST 使用相同的观测栈配置；比较结论 MUST NOT 建立在观测栈开启状态不同的两次运行之间。
- **FR-024**: 启动说明 MUST 覆盖固定端口 55432、9091、9090、9187、3000 的占用检查责任：基准入口检查 55432 和 9091，观测栈 Compose 检查 9090 和 9187，回看阶段检查 3000；对应组件 MUST 明确报错，不静默改用其他端口。
- **FR-025**: 同一时间 MUST NOT 存在两个使用这些固定端口的压测运行；基准入口 MUST 通过排他文件锁保证这一点，后启动的一方 MUST 立即拒绝运行，不共享或覆盖数据目录；端口检查作为辅助。
- **FR-026**: 压测被中断时，指标证据检查 MUST 只判定实际完成的测量阶段；窗口终点取实际结束时间，未运行的阶段记为缺失，整体 MUST 标记为不完整。
- **FR-027**: 观测栈容器 MUST 以宿主 UID/GID 运行，密码文件只读挂载；回看 MUST 把归档复制到临时目录后再启动 Prometheus，归档目录 MUST 保持不变。
- **FR-028**: exporter MUST 显式关闭 `settings`、`stat_activity`、`stat_user_tables`、`statio_*`、`locks`、`replication*` 等高基数或带用户标签的 collector；锁等待 MUST 由不带用户标签的自定义查询提供，指标中 MUST NOT 出现 `usename` 或 `application_name`。
- **FR-029**: 证据检查 MUST 用抓取次数检测 Prometheus 自身中断；Prometheus 不可达时 MUST 写入不完整证据并给出原因；证据文件 MUST 先写临时文件再原子替换。
- **FR-030**: Grafana MUST 关闭 basic auth、登录表单和注册，只保留匿名 Viewer；数据源和看板 MUST 禁止 UI 修改回写；数据源或看板 provisioning 失败时 MUST 明确报错，不能以空看板继续。
- **FR-031**: PostgreSQL 监控角色的创建 MUST 通过 stdin 传递 SQL，不得使用带密码的命令行参数；日志和摘要 MUST NOT 记录密码。
- **FR-032**: 证据检查脚本 MUST 定义退出码：0 完整、3 不完整、2 参数或 IO 错误、4 Prometheus 不可达（同时写不完整证据）。
- **FR-033**: 关键指标序列清单 MUST 覆盖四类指标的验收查询，并在契约中逐项列出。

### Key Entities

- **运行标识**: 每次完整运行的唯一标识，关联 k6 结果、指标数据目录和摘要记录。
- **指标样本**: 带名称、标签、时间戳和值的只读数值，按时间序列保存。
- **指标证据标记**: 压测后生成的检查结果，按测量阶段记录时间窗、抓取目标状态、`pg_up` 和缺失的关键序列，用于判定该运行能否用于指标验收。
- **看板配置**: 随仓库版本管理的 Grafana 数据源和面板定义，可重复加载。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 每个测量轮 200 RPS × 120 秒压测后，四类指标能在同一时间窗查到，整轮服务端 P95 可与 k6 P95 对照；两者差异不超过 ±3ms 或 ±20%（取较大者），超出时需给出时间窗或桶边界解释。请求计数的差异只来自时间窗边界。
- **SC-002**: 能分别演示 exporter 停止（`up=0`）、数据库停止（`up=1`、`pg_up=0`）、数据库空闲（`up=1`、`pg_up=1`、事务速率接近 0）和有流量四种状态。
- **SC-003**: 能区分“连接池未饱和”和“连接池打满并出现等待”，并计算出等待次数与平均等待。
- **SC-004**: 能区分“数据库整体繁忙”和“数据库存在锁等待”。
- **SC-005**: 应用和 exporter 停止后，使用保存的数据目录副本仍能回看该次运行的完整时间窗；归档目录内容不变。
- **SC-006**: 两次运行使用不同订单号的压测，不产生由业务标识带来的新时间序列。
- **SC-007**: 从零按文档启动观测栈、跑完一次完整运行、归档数据并打开看板，不需要口头补充步骤。
- **SC-008**: 基准入口一次完整运行产生 5 个测量轮，每轮使用独立数据库和卷；任一轮失败时整次运行不合格。
- **SC-009**: 指标中断的运行产生 `metrics-evidence.json`，按测量阶段记录缺失项并标记“指标证据不完整”；其基准资格判定与无中断运行一致。
- **SC-010**: 按文档清理某次运行后，其数据库卷和证据目录消失，其他运行的数据不受影响。
- **SC-011**: 两次对照运行使用相同的观测栈配置（同时开启或同时关闭）；不得用开启观测栈的运行与未开启的历史运行直接比较。
- **SC-012**: 未设置 `PAYMENT_HUB_METRICS_ADDR` 时，应用不监听指标端口；设置后可从本机回环访问。
- **SC-013**: 55432/9091 被占用时基准入口拒绝运行；9090/9187 被占用时观测栈启动失败；3000 被占用时回看启动失败；均给出明确错误。
- **SC-014**: 中断的运行只判定已完成的测量阶段，未运行阶段记为缺失，整体标记 `incomplete`。
- **SC-015**: 按契约导出一次运行的关键查询，`metrics-export/` 下每个查询都有 CSV，并有一份 JSON 汇总；退出码为 0。
- **SC-016**: 未启动观测栈时，应用和基准仍能完成一次完整运行，基准资格不受影响。
- **SC-017**: 测量阶段只有 Prometheus 和 exporter 在运行，Grafana 容器不存在；回看阶段才启动 Grafana。
- **SC-018**: 第一个运行持有锁时，第二个运行立即失败并指出锁路径，不会覆盖第一个运行的数据。
- **SC-019**: PostgreSQL 指标中不存在 `usename`、`application_name` 标签；一次运行的序列总数低于契约预算。

## 非目标

- 常驻监控平台、公网访问、告警规则和通知渠道。
- 长期存储、远程写入、SLO 和容量规划。
- 支付结果指标（成功、失败、未知按业务口径计数）；该能力另立一期。
- 分布式追踪、pprof、日志聚合。
- 容器资源指标（cAdvisor）；应用当前作为宿主机进程运行。
- `pg_stat_statements` 逐条 SQL 统计。
- 生产环境部署和真实渠道监控。

## Assumptions

- 应用与 k6 在宿主机运行，PostgreSQL 在 Compose 容器中；这是当前压测入口的形态。
- 观测栈只在本机回环地址访问，不涉及生产网络和真实支付数据。
- 观测栈容器使用 host 网络；要求 Linux/WSL2 同一来宾的 Docker Engine，不支持 Docker Desktop 的独立虚拟机模式。
- Prometheus 和 exporter 以宿主 UID/GID 运行；密码文件通过只读挂载进入容器，容器内不检查权限。
- 时间统一使用 UTC；每个测量阶段记录的开始和结束时间用于对齐 k6 摘要。
- 基准构建将连接池上限固定为 16；普通构建使用默认值。
- 5 秒抓取间隔足以观察 120 秒压测的趋势；尖峰类问题通过累计计数回答。
- 观测栈由观察者手动启动和停止，归档按文档步骤执行；基准入口不负责起停观测栈。
- 观测栈不绑定 CPU；其自身开销未单独测量，若出现 k6 丢发，先排除观测栈影响再归因。
- 需要对比的两次运行必须使用相同的观测栈配置；绝对数值只在同一配置下比较，不与未启用观测栈的历史数据直接比较。
- 每次运行的证据目录和数据库卷不自动删除；观察者确认不再需要后，按文档命令清理。
- 基准的 PostgreSQL 使用固定回环端口 55432，并由排他文件锁保证同一时间只有一个运行；监控密码由观察者通过本地 `0600` 文件提供，不进入仓库、环境变量、命令行或日志。
- 本期将基准入口固定为 5 个测量轮；每轮使用独立数据库和卷，运行时长和磁盘占用相应增加。
- 原 3 轮实测记录只描述当时的协议和历史表现，不与 5 轮协议的结果直接比较。
- 现有 Go、Python 3.9+、k6 v2.4.0 和 Docker/Compose 工具链继续可用，不新增下载或安装步骤。
