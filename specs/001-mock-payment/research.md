# 技术取舍记录：当前范围设计

**Status**: Approved — 当前范围技术取舍已分轮确认；仅记录设计依据，不表示依赖、数据库或运行环境已经验证。

**Date**: 2026-11-06

**依据**: [已批准规格](spec.md)、[宪章](../../.specify/memory/constitution.md)及本次对话分轮获用户确认的设计。

**关联计划**: [plan.md](plan.md)

本文归档已确认的选择、理由和替代方案。R1–R5保留首轮总体结构取舍并同步已收敛的限制说明，后续条目补记数据、合同及运行发布设计；精确约束以对应源文档为准，不另复制一套完整合同。不生成新的业务承诺，也不作为实现或测试通过的证据；基础镜像、CI 引用和真实外部权限仍按计划在相关操作前核实。

## R1. Go 单体与内部模块分工

**Decision**: 采用一个 Go 应用进程，内部区分 HTTP 入口、支付业务、平台订单存储、Mock 和启动组装职责，使用普通构造函数手工连接依赖。

**Rationale**: 当前复杂度集中在支付意图唯一性、未知核实和确认结果保护，而非跨服务通信。单体便于理解完整调用过程、控制故障并定位问题；职责划分仍能让支付业务不依赖 HTTP 和数据库专用对象。

**Alternatives considered**:
- 拆分多个服务：会提前增加部署、通信和故障定位工作，当前单接入方、单 Mock 没有对应收益。
- 全部逻辑写入 HTTP 处理函数：会使 SQL、渠道调用与规则混杂，不利于独立验证。
- 引入依赖注入框架或大量转发层：当前模块数量和替换需求不足以证明维护代价合理，首期不采用。

**限制**: 目录职责与依赖方向现已记录于 [plan.md](plan.md)，具体类型和方法留到实现；不要求每个类型都有一个 Go 接口，新增接口须对应实际隔离或替换需要。

## R2. Mock 留在进程内，但保留独立交易事实

**Decision**: Mock 位于 Go 应用内部，拥有独立的交易记录。可以共用 PostgreSQL 实例和连接池，但不与平台登记或结果保存共用付款事务。使用中台事先保存的稳定编号关联与查询原交易。

**Rationale**: 这样既不必运行独立渠道服务，也不会抹掉“Mock 已成功、平台尚未确认”的关键故障窗口。后续查询有独立事实可核实，不依赖平台自己的订单结果来冒充渠道证据。

**Alternatives considered**:
- 无记录、随机返回结果的函数：无法稳定重现答复丢失后可查、重启后核实等场景。
- Mock 交易与平台结果放进同一事务：会消除需要验证的部分成功窗口，不符合故障模型。
- 独立 Mock 服务或数据库实例：当前可用内部模块与独立提交满足验证目标，暂不增加运行单元。

**限制**: 此设计不验证真实渠道的网络行为。场景由可信测试准备过程控制，不由普通商城付款请求指定；交易记录见 [data-model.md](data-model.md)，测试控制方案见计划，加载与控制代码尚未实现。

## R3. PostgreSQL、显式 SQL 与独立迁移

**Decision**: 平台使用 PostgreSQL、pgx 和手写显式 SQL；goose 作为独立迁移工具，首期不引入 sqlc 或 ORM。数据访问围绕完整能力封装，而不是要求 HTTP 入口拼装零散操作。

**Rationale**: 关键唯一约束、条件写入和事务范围应当清晰可见，也符合系统学习后端工程的目标。首期访问规模有限，暂不增加代码生成同步流程；独立迁移让数据库变更成为明确可检查的步骤。

**Alternatives considered**:
- ORM：并非无法满足需求，但本轮没有足以替代显式 SQL 路线的必要收益。
- sqlc：能够减少参数和结果映射代码；当前先不引入，后续若重复明显可在数据访问内部重新评估。
- 应用启动时自动改表：会模糊数据库变更与应用启动的责任和失败位置，本项目不采用。
- golang-migrate：同样可用；本次讨论选择 goose，不同时维护两套迁移方案。

**限制**: 工具不保证端到端恰好一次，也不代替事务、约束和业务测试。goose 的反向迁移不是发布失败时的自动恢复方案；版本与表结构已有设计，迁移文件和实际数据库行为尚未实现或验证。

## R4. 本地双容器演示与轻量 HTTP 客户端

**Decision**: 完整演示使用 Docker Compose 组织一个 Go 应用容器与一个 PostgreSQL 容器，数据库独立持久化。使用轻量客户端走真实 HTTP 入口，不建设商城服务或页面。

**Rationale**: 用户当前没有云服务器，本地足以学习和验证容器运行、数据保留、迁移与重启过程。真实 HTTP 调用保留接入链路，不把商城演示变成绕过业务的数据库操作。

**Alternatives considered**:
- 云服务器或托管平台：目前不作为运行前提，未来需要公开演示时再独立评估。
- 把数据库数据仅留在数据库容器的可写层：替换该容器时会丢失数据，不符合数据独立持久化的方向，不采用。
- 完整商城应用：超出首期范围，会分散付款闭环的实现和验证精力。

**限制**: 本地可运行不代表公网部署、HTTPS 或高可用已经就绪。开发、测试和演示数据仍需隔离，具体运行配置及命令留待验证与交付阶段。

## R5. 查询触发核实，有界处理与明确生命周期

**Decision**: 提交在有界请求处理流程中编排，未知结果由后续查询触发核实，不新增后台扫描或自动补付。已取得可靠结果的必要保存工作有有限收尾安排，资源由启动退出流程统一管理。

**Rationale**: 与已批准的“提交、查询、不重付”边界一致，避免把进程内 goroutine 误当作可持久恢复的付款任务系统。正常停机尽量收尾，突然退出则依靠已保存的事实继续查询和复用。

**Alternatives considered**:
- 先回复受理，再启动无人管理的 goroutine 付款：没有持久任务和恢复保证，不能据此承诺后续必定完成。
- 自动扫描未知订单并重新付款：违反首期不产生第二次支付尝试的约束。
- 无限等待最终结果：会使请求和停机无界，不采用。

**限制**: 无人查询时，平台结果可能继续停留在未知。首期不承诺自动续跑所有未完成付款；期限与有限收尾方案见计划，实际超时、取消与退出行为仍须实现和验证。

## R6. 三类事实、业务唯一键与短事务

**Decision**: 使用平台支付订单、Mock 交易、结果处理记录三张业务表。以“接入方＋业务订单号”唯一定位支付意图；读已提交下采用唯一键登记、独立读取及保存时的单订单短行锁，Mock 调用始终在平台事务之外。新确认与最小依据原子保存，提交不明先核对，不恢复付款资格。

**Rationale**: 分开表达订单、渠道事实和处理依据，使答复丢失、并发核实及提交不明仍能按保存事实解释；完整原子动作避免调用者拼接半套保存。

**Alternatives considered**:
- 仅凭应用先查后写防重：不能代替数据库唯一约束。
- 跨 Mock 调用持有平台事务或以更高隔离级别包办流程：扩大锁范围，也不能消除渠道与平台分别提交的不确定性。
- 用单个最后错误字段覆盖历史：无法解释独立核实和保存重试，不采用。

**限制**: 字段、取值、证据白名单、编号与时间、记录重试及 SQL 语义以 [data-model.md](data-model.md) 为准；当前没有迁移或真实并发测试证据，追踪故障不承诺自动补齐。

## R7. 单笔资源合同与分开的支付、HTTP 语义

**Decision**: 使用一个提交入口和两种单笔查询定位，均限定可信接入方；采用已批准的 Bearer API key 映射、严格输入、互斥的错误与订单问题包装，以及明确状态码和禁存储缓存边界。

**Rationale**: 支付结果与本次处理问题分开，既不把超时猜成失败，也不因额外追踪故障隐藏已有确认结果；同一意图只有一笔订单，不增加列表或管理能力。

**Alternatives considered**:
- 只靠 HTTP 2xx 表示付款成功：无法表达未知、明确失败及追踪问题。
- 首次响应永久冻结，或未知一律返回202暗示后台续跑：与当前事实查询和无自动续跑的设计不符。
- 先建设登录、JWT/OAuth 或商户管理系统：当前单演示接入方没有相应需要。

**限制**: 详细字段、拒绝优先级、媒体类型、大小和状态码以 [HTTP 合同](contracts/http-api.md) 为准。演示鉴权不是生产安全保证，服务器提前拒绝的畸形请求也不保证业务 JSON 包装。

## R8. 分层验证与跨重启独立观测

**Decision**: 分别以业务规则、真实 PostgreSQL、HTTP 集成和真实进程重启验证关键承诺，并另设实际镜像关卡。测试父进程跨应用重启保持，通过仅测试启用的私有 Unix domain socket、同步观测和有界屏障记录调用；Mock 交易效果另行核对。

**Rationale**: Mock 自身防重可能掩盖重复调用，内存计数又可能随应用重启清零。独立观察器与真实存储事实分开取证，能更诚实地验证受控故障窗口。

**Alternatives considered**:
- 用交易行数或结果处理记录数代替付款调用数：不能发现被 Mock 挡住的第二次调用。
- 用重新创建对象代替进程重启，或仅凭异步日志没出现事件判断零调用：证据不足。
- 增加业务计数表、常驻控制服务或可靠审计队列：超出当前验证目标，暂不采用。

**限制**: 每次真实调用有独立身份，观察器不替业务防重；缺口判不确定或失败，不承诺任意崩溃下无缺口审计。受控提交答复丢失不等于真实断链测试，也不将宿主二进制结果冒充镜像已验收。

## R9. 有界生命周期与分开的追踪证据

**Decision**: 启动、迁移、读取、主处理、Mock、数据库和退出各有明确预算；已观察取消后不再开始新的付款或核实，每请求仅有一次共享有限收尾。运行日志使用白名单 UTC JSON，项目级轮转；验收产物独立采集并跨重启保持。

**Rationale**: 不能无限等待，也不能因取消就推断已发生事实消失；数据库处理记录、运行日志和验收产物各有证明责任，任何一种都不能替代其余证据。

**Alternatives considered**:
- 每条 SQL、每次重试重新领取完整期限：可能使整体处理无界。
- 客户端断开就宣称事务回滚，或另开无人管理后台付款：均不符合首期语义。
- 仅依赖容器日志保留完整历史：轮转和移除容器可能丢失证据。

**限制**: 具体期限、轮转值和保留策略以计划为准，不是性能实测或 SLA；采集不完整不算留痕通过，日志和追踪故障不能降级已确认付款事实。

## R10. 双镜像配对、同产物验收与人工发布

**Decision**: PR 与默认分支更新做最小只读检查；人工发布仅接受默认分支受信提交。固定源码后各构建一次应用与迁移工具镜像，验收原产物后推送，再按最终远端摘要拉回复核；首期仅覆盖 `linux/amd64`，本地由人选配对摘要并显式迁移和启动。

**Rationale**: 源码测试、实际镜像、仓库内容与部署分别有证据，避免构建后换产物或凭标签漂移。迁移镜像包含对应工具和 SQL，使选用关系可以追溯。

**Alternatives considered**:
- 任意 PR、分支或手动按钮都能取得发布写权限：扩大不可信代码的权限，不采用。
- 每个阶段重新构建，或仅依赖 `latest`：无法确认部署的是验收过的内容。
- 发布失败自动降级迁移或删卷恢复：不保证数据库兼容，可能破坏事实，不采用。

**限制**: 源码 SHA、本地镜像 ID 与 registry manifest digest 不等价；CI 绿灯或推送完成都不单独证明可部署。真实仓库、包关联、权限、可见性和托管保留上限未配置，不自动公开或创建资源。

## R11. 可复现版本与轻量目录

**Decision**: 核心工具和依赖采用计划中的精确基线，项目执行禁止隐式切换 Go 工具链；goose 是独立 CLI。使用一个 Go module、一个入口，按当前职责组织内部包；只为实际依赖替换或故障控制定义小接口。

**Rationale**: 固定实际工具链和依赖便于复查同一构建，职责与依赖方向让业务规则不受 Gin 或 pgx 专用对象牵引；不为未来 SDK 或通用框架增加维护成本。

**Alternatives considered**:
- 工具、依赖与镜像一律使用 `latest`：运行输入会漂移。
- 仅凭 `go.mod` 声明或 `go.sum` 就认为实际工具链及所有依赖已锁定：混淆版本选择与校验信息。
- 先建公共 SDK、通用工具包或每个结构体对应一个接口：当前没有足够需要，不采用。

**限制**: 版本声明相容不等于编译或联调通过；基础镜像变体、真实摘要及 CI 引用仍须核实。不得因选版自动升级宿主工具，具体代码、命令和运行结果以 [运行指南草案](quickstart.md) 的后续补齐与实际证据为准。
