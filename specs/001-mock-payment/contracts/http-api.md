# HTTP Contract: 模拟商城一次性 Mock 支付闭环

**Status**: Approved — 当前范围三个业务入口的设计已分八轮评审确认，并纳入已批准技术计划；接口实现与运行验证尚未开始。

**Date**: 2026-11-06

**Spec**: [spec.md](../spec.md) | **Data Model**: [data-model.md](../data-model.md) | **Plan**: [plan.md](../plan.md)

本文记录用户已确认的业务路径、鉴权身份、输入、响应、拒绝优先级、状态码及 HTTP 边界。范围限于下述三个业务入口，不生成应用实现、额外路由、服务器配置或可执行测试。

## 资源含义与命名

- 对外使用简短资源名 `payments`，其业务含义仍是平台支付订单，不是 Mock 渠道交易、商城业务订单或单次 HTTP 请求。
- 此命名不要求改动内部模型或数据库表名 `payment_orders`，也不提供普通增删改查能力。
- 首期业务前缀为 `/api/v1`。接口版本不属于支付意图唯一标识，不得因更换入口版本而创建第二次付款。

## 业务路径

下表使用 `{payment_id}` 表示路径参数；第三条的定位信息位于查询参数中，不是另一段路径。

| 方法 | 路径 | 用途与定位输入 |
|------|------|----------------|
| `POST` | `/api/v1/payments` | 提交付款，登记新订单或复用已有订单；请求体与校验规则见下文 |
| `GET` | `/api/v1/payments/{payment_id}` | 按平台支付订单号查询，`payment_id` 对应平台订单 UUID，不是 Mock 交易号或请求编号 |
| `GET` | `/api/v1/payments` | 必须提供查询参数 `business_order_no`，结合当前已验证接入方精确查询一笔订单 |

业务订单号查询示例：`GET /api/v1/payments?business_order_no=M100`。

首期仍然只有提交与查询两个业务动作；两个 GET 是同一查询能力的两种定位方式。

## 定位与访问范围

1. 三个业务入口均先验证 `Authorization` 中的 Bearer API key，由服务端配置映射得到可信接入方身份，具体规则见下节。
2. 不允许调用者用 URL 或请求体中的 `client_id` 覆盖已验证身份；POST 请求体不接收该字段，出现时按未知字段拒绝，不据此切换商城身份。
3. 按业务订单号查询，实际定位键是“已验证接入方标识＋business_order_no”。订单号遵守数据模型中已确认的长度、字符范围和大小写规则。
4. 按平台订单号查询，也必须限定在当前已验证接入方范围内。知道一个平台 UUID 不等于获得跨上下文读取权限。
5. 两种定位方式关联同一平台订单，不生成不同类型的订单。首次提交答复丢失时，接入方可用原业务订单号找回订单，无须换号重新付款。

## 鉴权与接入方身份

### 凭据请求头与身份映射

三个业务入口仅通过一个 `Authorization` 请求头携带 API key：

```http
Authorization: Bearer <API_KEY>
```

- `<API_KEY>` 是占位符，不是真实密钥。首期使用配置的随机演示密钥；Bearer 只是携带方式，不要求密钥为 JWT，也不引入 OAuth 服务或登录系统。
- 仅接受一个 `Authorization`，不从 URL、JSON 或其他请求头寻找替代凭据。头名称与 Bearer 方案名按 HTTP 规则不区分大小写，密钥值本身区分大小写并按原值匹配。
- 有效密钥映射到运行配置中的唯一 `client_id`，验证通过后才将可信身份交给支付业务。密钥不是接入方标识，不从密钥内容或调用者提交的 `client_id` 推导身份。
- 换密钥不改变原接入方身份，不改变订单所属范围或支付意图唯一键，也不能借此绕过幂等规则。原有请求体及查询参数中的未知字段拒绝规则保持不变。

### 验证失败

缺少、重复、格式错误、空密钥或密钥不匹配时，统一返回 HTTP `401` 和 `error.code = UNAUTHORIZED`，使用既定的 `request_id + error` 包装，不读取订单、不调用 Mock。

所有上述401响应均携带以下挑战头：

```http
WWW-Authenticate: Bearer realm="payment-hub"
```

错误说明不回显密钥，不透露具体匹配情况；不能因校验失败退化为匿名业务访问，也不能用请求中的身份字段替代凭据验证。

### 配置与安全边界

- 密钥及接入方身份从运行配置加载；缺失或无效时启动失败，不提供默认密钥或免鉴权兜底。接入方标识仍须符合数据模型的格式规则。
- 使用随机生成的演示密钥，不将密钥写入 Git、日志或错误响应；本文件不创建真实密钥，具体配置操作留到运行设计阶段。
- 本地 HTTP 仅作为受控演示例外；跨不可信网络或公网必须使用 HTTPS。Bearer 本身不加密，不能将演示级鉴权宣称为生产安全已就绪。
- 首期不提供密钥发放、登录或管理接口，不扩大为商户管理系统；缓存、媒体类型和请求体大小按下节约定。

## 统一 HTTP 输入与响应边界

### POST 媒体类型与查询参数

- POST 必须声明一个 `Content-Type: application/json`，允许附带一个 `charset=utf-8`；不接受其他媒体类型、字符编码、额外媒体类型参数或重复声明。媒体类型和字符集标签按 HTTP 规则比较。
- 请求内容必须是 UTF-8。媒体类型正确但内容不是有效 UTF-8，或 JSON、字段不合法时，按输入无效返回 `400` 和 `INVALID_REQUEST`，不静默替换非法内容。
- 不支持压缩请求体，`Content-Encoding` 只允许省略或 `identity`；不解压 `gzip` 等输入后继续处理。
- 媒体类型缺失、不支持、重复声明或内容编码不受支持时，返回 `415` 和 `INVALID_REQUEST`。
- POST 不接受查询参数，支付字段只从约定的 JSON 请求体读取；额外查询参数按输入无效返回 `400`，不能覆盖请求体或身份。
- 两个 GET 不要求 `Content-Type`，仍拒绝任何非空请求体并返回 `400` 和 `INVALID_REQUEST`，不从请求体取查询条件。

### POST 请求体大小与检查顺序

- POST 请求体内容最多4 KiB，即4096字节，包含上限；限制按实际字节数判断，包含全部 JSON 内容和空白，不只是已解析字段。
- 超过4096字节时返回 `413` 和 `INVALID_REQUEST`。按实际读取字节限制，不能只信任 `Content-Length`；完成受限读取与校验前，不得先登记订单或调用 Mock。
- 4096字节是本项目小型演示接口的保护值，不宣称 Go、HTTP 或支付行业通用限额。
- 先鉴权，再检查 POST 媒体类型、内容编码和大小，然后执行既定结构、类型、定位及冲突规则。未通过鉴权仍优先返回 `401`；不因请求体问题绕过身份验证。

### 统一 JSON 响应与缓存

三个业务入口的应用响应，包括正常订单、带 `issues` 的订单及错误响应，都使用 UTF-8 JSON，并包含：

```http
Content-Type: application/json
Cache-Control: no-store
```

- 只提供 JSON，不提供表单、XML、HTML 等响应表示，也不建设多格式内容协商。
- 首期不生成 `ETag` 或 `Last-Modified`，不使用 `304` 绕过本次业务查询，不主动建立以旧支付结果代替查询的缓存流程。
- `no-store` 不删除此前已有缓存，也不能替代密钥、日志和其他信息保护；不能据此宣称敏感信息已被全面清除。
- 上述 JSON 包装和响应头约定覆盖进入应用处理的请求；HTTP 服务器在进入应用前已拒绝的畸形请求，不承诺同样的业务 JSON 包装或请求编号。

## POST 请求体与输入校验

`POST /api/v1/payments` 的请求体只包含以下三个必填字段：

```json
{
  "business_order_no": "M100",
  "amount": 100,
  "currency": "CNY"
}
```

示例中的 `amount: 100` 表示100分，即1元，不是100元。

| 字段 | JSON 类型 | 规则 |
|------|-----------|------|
| `business_order_no` | 字符串 | 必填，1～64位 ASCII 英文字母、数字、短横线或下划线；区分大小写，不自动裁剪空格、转小写或截断 |
| `amount` | 数字，且必须使用整数字面量 | 必填，以分为单位，范围为1～1,000,000，两端包含；不能使用字符串、小数或指数形式 |
| `currency` | 字符串 | 必填，只接受准确的 `CNY`，不自动去空格或转大写 |

### 严格解析规则

- 请求体必须是语法合法的单个 JSON 对象。拒绝空请求体、顶层 `null`、数组、其他标量、多个拼接对象，以及对象后的非空白内容。
- 字段名必须准确匹配上表，区分大小写；三个字段均不得缺失或为 `null`，值的类型必须符合约定。
- 拒绝未知字段，不静默忽略。接入方身份由已验证凭据确定，不在请求体重复传入；`client_id`、平台订单号、支付结果或 Mock 场景等额外字段均不能作为可写入属性提交。
- 同一个字段出现两次时拒绝整个请求，不采用“第一个值”或“最后一个值”，避免金额含义不明确。
- 金额只接受 `100` 这样的十进制整数字面量。`"100"`、`100.0`、`1e2` 等表示均拒绝，不自动转型、舍入或取整；解析、比较和运算不得经过二进制浮点数。
- 上述校验失败时，不创建或占用支付意图、不调用 Mock，也不改变已有订单。

以上规则不改变已确认的订单复用与冲突保护要求：相同支付意图及相同参数复用原订单；金额或币种冲突必须拒绝，不得覆盖原事实或通过修改请求体再次付款。错误表达、拒绝优先级及 HTTP 状态码见后文。

## GET 输入与校验

### 按平台支付订单号查询

`GET /api/v1/payments/{payment_id}`：

- `payment_id` 必须是标准带连字符的 UUIDv4，共36个字符；十六进制字母大小写均可。
- 不接受短号、花括号或其他编号格式，也不能用 Mock 交易号或请求编号替代平台订单号。
- 此入口不接受查询参数，不通过同时传入业务订单号等条件来选择另一种定位方式。

### 按商城业务订单号查询

`GET /api/v1/payments?business_order_no=M100`：

- 必须且只能提供一个名为 `business_order_no` 的查询参数，不能缺少或为空。
- 值经正常 URL 解码后，按1～64位 ASCII 英文字母、数字、短横线或下划线校验；区分大小写，不裁剪空格、转小写或截断。
- 格式不合法或 URL 编码错误时拒绝请求，不将其解释为无记录。
- 同名参数重复时拒绝请求，即使重复的值相同也不接受。
- 拒绝其他查询参数，包括 `client_id`、`page`、`limit`；不能借查询参数切换接入方身份或扩展为列表查询。

### 共同输入边界与业务含义

两种 GET 都不接收请求体；非空请求体必须拒绝，不从请求体读取或覆盖定位条件。

| 情况 | 业务含义 |
|------|----------|
| 定位信息缺失或格式不合法 | 输入无效，不能直接表述为订单不存在 |
| 输入合法，但当前已验证接入方范围内找不到订单 | 无记录，不是支付失败 |
| 找到订单 | 已有确认结果直接读取；未知结果必须向 Mock 核实原交易 |

上述输入规则不改变查询的业务边界：查询不得创建支付订单，也不得触发新的付款。错误与异常响应结构及 HTTP 状态码见后文。

## 正常订单响应

三个业务入口共用 `request_id` 加 `payment` 的单笔结构。POST 返回本次登记或复用的订单，两种 GET 返回找到的订单；按业务订单号查询也使用对象，不返回数组。本节确定正常订单响应，错误与异常结构及 HTTP 状态码见后文。

```json
{
  "request_id": "0d7476ac-a7c9-4b7b-bbe2-61c353eb78e7",
  "payment": {
    "payment_id": "8b3e19bd-909a-467d-94c7-bf713984f03c",
    "business_order_no": "M100",
    "amount": 100,
    "currency": "CNY",
    "result": "UNKNOWN",
    "registered_at": "2026-11-06T09:00:00Z",
    "confirmed_at": null
  }
}
```

### 外层与订单字段

- `request_id` 是入口为每次 HTTP 请求生成的 UUIDv4 字符串，用于定位问题，不是幂等键。重放产生新的请求编号，但仍关联原支付订单。
- `payment` 为单个订单对象，包含以下七个字段，均返回；仅 `confirmed_at` 按结果允许为 `null`。

| 字段 | JSON 类型 | 含义与返回规则 |
|------|-----------|----------------|
| `payment_id` | 字符串 | 平台支付订单号，统一输出小写、带连字符的 UUIDv4；重复提交不换号 |
| `business_order_no` | 字符串 | 订单原始业务订单号，保留大小写，不用本次冲突请求的值替换 |
| `amount` | 整数 | 订单原始整数分金额，范围仍为1～1,000,000，两端包含 |
| `currency` | 字符串 | 订单原始币种，首期为 `CNY` |
| `result` | 字符串 | 平台当前可可靠返回的支付结果，取值见下表 |
| `registered_at` | 字符串 | 平台登记时间，采用下述统一时间格式 |
| `confirmed_at` | 字符串或 `null` | 平台本地确认时间；未知时明确返回 `null`，已确认成功或失败时必须有值 |

### 支付结果与时间

| `result` | 含义 |
|----------|------|
| `SUCCEEDED` | 平台已确认付款成功 |
| `FAILED` | 平台已确认付款失败，不等于服务器出错 |
| `UNKNOWN` | 目前无法确认，不等于失败，也不意味着后台正在自动重付 |

- 不增加容易与付款成功混淆的 `success` 布尔字段。取得并返回订单不等于付款成功，调用方应读取 `payment.result`。
- 响应中的确认结果必须来自平台已可靠保存的事实，不能把尚未确认提交的更新当作落库成功。
- 所有返回时间统一为 UTC 的 RFC3339 字符串，末尾为 `Z`，允许小数秒。登记时间与本地确认时间保持各自含义，不冒充 Mock 实际处理时间。
- 相同意图的重复请求可以返回后来已确认的结果，不永久冻结首次响应；原始金额、币种和业务订单号不得被冲突请求改写。
- 首期不返回接入方标识、Mock 交易号、内部结果处理记录或核实证据，不将内部存储模型直接对外暴露。

`UNKNOWN` 只表达订单结果，不能说明本次核实是否遇到故障。本次处理问题须按下文的 `error` 或 `issues` 明确报告，不能靠返回 `UNKNOWN` 悄悄吞掉故障；额外追踪失败也不得降级已经能够读取的确认结果。HTTP 状态码按后文映射，不由支付结果单独决定。

## 错误与异常响应

本节区分本次请求的处理问题与订单支付结果，不将接口错误直接转换为 `payment.result = FAILED`。

### 请求拒绝或无法可靠返回订单

使用 `request_id` 加 `error`，不带 `payment` 或 `issues`。`error` 必须包含字符串 `code` 和 `message`；即使能找到原订单，输入拒绝、身份未验证或参数冲突仍使用该包装。

```json
{
  "request_id": "cc894a81-d54a-4d6b-a321-238ffad9920b",
  "error": {
    "code": "PAYMENT_CONFLICT",
    "message": "该业务订单已有不同的金额或币种"
  }
}
```

| 错误码 | 含义与边界 |
|--------|------------|
| `INVALID_REQUEST` | HTTP 输入边界不符合约定、输入无法按合同解释，或新支付意图的业务值无效；与参数冲突同时涉及的情况按下文优先级判断 |
| `UNAUTHORIZED` | 未能验证接入方身份，不读取订单或调用 Mock；凭据与401挑战按前文鉴权规则处理 |
| `PAYMENT_NOT_FOUND` | 定位信息合法，但当前已验证接入方范围内没有平台订单；不能用于表示 Mock 无匹配记录或数据库读取失败 |
| `PAYMENT_CONFLICT` | 同一支付意图的可比较金额或币种与已有订单不同，不修改原事实或发起付款 |
| `PROCESSING_ERROR` | 平台处理发生故障，无法可靠完成本次请求；不能据此宣称事务已回滚、平台订单不存在或付款已失败 |

调用方按稳定的 `code` 判断，不按 `message` 文案分支。`message` 使用受控、脱敏的说明，不暴露 SQL、凭据或原始异常，也不拼造订单或返回未经确认登记的候选订单编号。

### 已有可返回订单，但本次处理存在问题

已接受或复用订单后，若有可靠的订单事实可返回，则保留原 `payment` 对象，增加非空 `issues` 数组。每项包含字符串 `code` 和脱敏的 `message`；没有本次问题时省略 `issues`，不返回空数组。

`error` 与 `payment + issues` 两种包装互斥，不在同一响应中混用。已可靠保存的明确付款失败仍是正常的 `payment.result = FAILED`，不能仅因此返回处理错误。

| 问题码 | 含义与边界 |
|--------|------------|
| `MOCK_RESULT_UNCONFIRMED` | 本次付款调用或查询未能取得可用 Mock 答复，包括超时、通信故障等；不代表已确定付款失败 |
| `MOCK_RESULT_NOT_FOUND` | 平台订单存在，但本次查询没有取得匹配的 Mock 记录；不得据此报平台无订单或重新付款 |
| `MOCK_EVIDENCE_REJECTED` | Mock 依据存在错配、冲突或无效信息，不据此推进或覆盖平台结果 |
| `RESULT_SAVE_ERROR` | 本次结果保存失败或提交情况无法确认；登记提交不明而已能可靠读回订单时，也用该码报告本次保存的不确定性，不表示订单支付结果为失败 |
| `TRACE_SAVE_ERROR` | 本次追踪保存失败或无法确认；说明中如实区分已知失败与提交不明，不能声称记录已落库 |

以下示例表示已有确认成功结果可以可靠返回，但本次额外追踪保存失败；不表示普通读取已确认订单时必须新增业务核实记录。

```json
{
  "request_id": "f2cac80a-3494-40c5-91c0-0286c95abb6e",
  "payment": {
    "payment_id": "8b3e19bd-909a-467d-94c7-bf713984f03c",
    "business_order_no": "M100",
    "amount": 100,
    "currency": "CNY",
    "result": "SUCCEEDED",
    "registered_at": "2026-11-06T09:00:00Z",
    "confirmed_at": "2026-11-06T09:00:01Z"
  },
  "issues": [
    {
      "code": "TRACE_SAVE_ERROR",
      "message": "本次核实记录保存失败"
    }
  ]
}
```

- 同次请求可以报告多个问题，例如查询核实故障加追踪保存问题；问题只描述本次处理，不把历史故障当成本次故障重复返回。
- 已可靠读取的确认结果仍可返回，不因额外追踪写入失败而降级或阻断，也不为报告该额外故障强制依赖一次新的成功读取。
- 正常路径仍须保存应有的核实记录；保存失败仍须明确报告并留下受控脱敏日志。`issues` 不是记录已保存、追踪验收通过或事后自动补齐的证明。

### 提交不明与付款资格

- 提交不明时先按数据模型读回订单及同次处理记录核对；可靠读到订单不等于证明本次保存已经完成。
- 能可靠取得订单事实时才带 `payment`，本次保存仍有问题则同时报告；无法核实时返回处理错误，不拿旧 `UNKNOWN` 快照或 Mock 新答复冒充当前已保存结果。
- `issues.message` 同样不能旁路宣称尚未可靠保存的新成功或失败。处理错误不代表已回滚，查询失败也不代表无记录。
- 登记提交不明后即使读到了订单，也不能重新领取付款资格；任何错误或问题码都不授予重付、自动切换渠道或重置订单的许可。

## 拒绝优先级与限定只读核对

1. 先验证接入方身份，再检查严格 JSON 结构、字段、类型、金额表示及定位格式；缺字段、重复字段、小数或指数金额等无法按合同安全解释的输入直接拒绝。
2. 对可安全比较的金额和币种，已有订单事实不同则优先报 `PAYMENT_CONFLICT`；例如已有 `M100 / CNY` 时重放 `M100 / EUR`，明确按冲突拒绝。
3. 对全新支付意图，金额越界或币种非 CNY 等业务值不合法时报 `INVALID_REQUEST`，不得登记或付款。

具体补充仅限“结构完整、可安全比较，但金额范围或币种不合法”的分支：按当前已验证接入方和业务订单号做一次普通只读定位。可靠读到既有不同事实则报冲突，可靠查无订单则报输入无效；读取失败报处理错误，不能推定订单不存在。

该读取不是会核实未知结果的 GET 业务流程，不调用 Mock，不创建或改写订单，也不授予付款资格。有效提交仍沿用既定登记及唯一键冲突读取流程；全部业务值校验仍在登记事务之前完成，不放宽金额或币种要求。本节仅补充拒绝原因的判断，不新增 HTTP 入口或数据库实现。

## HTTP 状态码与配套约束

状态码表达本次 HTTP 请求如何完成，`payment.result` 表达付款事实，`issues` 表达本次处理问题；三者不能互相替代。本节仅约定上述三个业务入口的应用响应，输入边界见前文，不扩展为其他路由或底层 HTTP 拒绝的保证。

### 能可靠返回订单的响应

| 场景 | HTTP 状态码 |
|------|-------------|
| POST，确认是本次新建且登记已提交的订单 | `201 Created` |
| POST，复用已有订单 | `200 OK` |
| 两种 GET，找到并返回订单 | `200 OK` |

- `201` 仅表示平台订单已创建，不表示付款成功；新订单的结果可以是 `SUCCEEDED`、`FAILED` 或 `UNKNOWN`。
- 返回 `201` 时必须附 `Location`，指向该平台订单的查询 URL，使用实际平台订单号，例如：

```http
Location: /api/v1/payments/8b3e19bd-909a-467d-94c7-bf713984f03c
```

- 登记提交不明后仅仅读到订单存在，不能据此宣称本次新建或返回 `201`，也不能恢复付款资格；若可按既有订单事实返回，则使用 `200` 并明确报告本次问题。
- 若无法可靠返回订单而进入 `error` 包装，按下表处理，不能因为此前曾经登记过订单就固定返回 `201`。
- 存在 `issues` 时仍按上述新建、复用或查询规则使用 `201` 或 `200`；`2xx` 不证明付款成功、处理无异常或追踪验收通过，调用方必须检查 `payment.result` 和 `issues`。
- 平台订单存在但 Mock 无匹配记录时，查询返回 `200`、已有订单结果及 `MOCK_RESULT_NOT_FOUND`，不是 `404`；未知订单保持 `UNKNOWN`。
- 已有成功结果但额外追踪保存失败时，查询仍返回 `200`、`SUCCEEDED` 和 `TRACE_SAVE_ERROR`，不降级已确认事实，也不宣称追踪成功。
- `UNKNOWN` 不自动映射为 `202`；首期返回订单当前事实，不通过状态码暗示后台会自动续跑。

### 返回 error 的响应

| `error.code` 与条件 | HTTP 状态码 |
|-------------------|-------------|
| `INVALID_REQUEST`：JSON、字段、业务值或其他已约定输入不合法 | `400 Bad Request` |
| `INVALID_REQUEST`：POST 请求体超过4096字节 | `413 Content Too Large` |
| `INVALID_REQUEST`：POST 媒体类型、声明或内容编码不受支持 | `415 Unsupported Media Type` |
| `UNAUTHORIZED` | `401 Unauthorized` |
| `PAYMENT_NOT_FOUND` | `404 Not Found` |
| `PAYMENT_CONFLICT` | `409 Conflict` |
| `PROCESSING_ERROR`：数据库等依赖暂不可用，或操作超时而无法可靠完成本次请求 | `503 Service Unavailable` |
| `PROCESSING_ERROR`：其他未预期的内部故障 | `500 Internal Server Error` |

- JSON 结构、字段和业务值错误用 `400`，不另拆 `422`；POST 大小及媒体类型、内容编码边界分别用 `413` 和 `415`，仍使用 `INVALID_REQUEST`，不新增支付结果类别。已有事实冲突仍按拒绝优先级返回 `409`。
- `401` 必须包含前文确定的 `WWW-Authenticate: Bearer realm="payment-hub"` 挑战头，不把缺少该头的响应当成完整合同实现。
- `500` 或 `503` 均不证明事务已回滚、订单不存在或付款失败，也不授予换业务单号重付的许可。
- 不编造恢复时间或随意附加 `Retry-After`；状态码不代替按原支付意图查询和核实。

## 提交与查询的业务保证

### 提交付款

- POST 不表示每次都创建新付款；同一支付意图及相同参数复用原订单，金额或币种冲突则拒绝本次请求，不改写原记录。
- 付款资格、结果确认和异常处理沿用规格及数据模型，不能因为 HTTP 层重试而重新执行渠道付款。
- 已确认失败的订单重复提交仍返回原失败结果，首期不支持重新支付。

### 查询付款

- 两种 GET 都是单笔查询，不是订单列表。集合路径缺少 `business_order_no` 时拒绝请求，不退化为无条件列表。
- 不提供模糊搜索、分页或批量订单查询；查询参数不是额外创建付款资格的方式。
- 不存在对应平台订单时以 `404` 和 `PAYMENT_NOT_FOUND` 明确表达无记录，不创建支付订单，也不调用 Mock 发起付款；不将 Mock 无匹配或读取故障混为平台无记录。
- 已有确认结果时读取并返回；未知时必须向 Mock 核实原交易，取得匹配的确认结果后按数据模型保存确认与依据，仍无法确认则保留未知；不得创造新的支付意图、支付尝试或模拟付款效果。
- 两种查询采用相同的单笔查询业务语义，正常订单响应均使用上文的 `payment` 对象，不返回数组。

## 不开放的业务能力

- 不提供修改金额、删除订单、重置付款、强制成功或强制失败的入口。
- Mock 场景控制不作为商城业务入口，也不由普通付款请求指定结果。
- 本轮不注册其他查询别名或管理路径。健康检查和可信测试准备方式留待运行与验证设计，不在本轮补充路径。
