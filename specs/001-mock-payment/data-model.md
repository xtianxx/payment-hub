# Data Model: 模拟商城一次性 Mock 支付闭环

**Status**: Approved — 当前范围的数据模型与关键事务设计已分四轮评审确认，并纳入已批准技术计划；数据库实现与运行验证尚未开始。

**Date**: 2026-11-06

**Spec**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md)

本文记录平台支付订单、Mock 渠道交易和结果处理记录的信息含义、数据库字段映射、关键约束及短事务方案。数据库名称不直接决定对外 API 字段；本文件不生成建表语句、迁移或应用代码，也不表示约束已经实现或测试通过。

## 平台支付订单

平台支付订单表达并跟踪一项支付意图，不等于商城业务订单、单次 HTTP 请求或渠道交易。首期使用“接入方标识＋商城业务订单号”唯一识别支付意图，不另造独立支付意图编号，也不增加支付尝试表。

### 信息组成

对应表名为 `payment_orders`。

| 信息 | 数据库字段 | 类型与空值 | 含义与记录规则 |
|------|------------|------------|----------------|
| 平台支付订单号 | `id` | `UUID`，主键 | 应用生成 UUIDv4；登记、查询、重启及重复请求关联同一订单，不为重试另建订单 |
| 接入方标识 | `client_id` | `TEXT`，非空 | 已验证的业务身份，不是 API key；不随换钥匙改变，格式见通用约定 |
| 商城业务订单号 | `business_order_no` | `TEXT`，非空 | 与接入方一起定位同一支付意图，格式见通用约定 |
| 金额 | `amount` | `BIGINT`，非空 | 整数分，Go 使用 `int64`；范围为 1～1,000,000 分，两端包含，不因类型范围更大而放宽 |
| 币种 | `currency` | `TEXT`，非空 | 首期仅 CNY；与原金额一起作为不可被重复请求改写的付款事实 |
| 支付结果 | `result` | `TEXT`，非空 | 取 `UNKNOWN`、`SUCCEEDED`、`FAILED`；登记时显式保存 `UNKNOWN`，不默认成功 |
| 已关联的 Mock 交易号 | `mock_transaction_id` | `UUID`，可空 | 取得并核对后保存；有值时唯一，暂缺不能证明未付款或取得重付资格 |
| 登记时间 | `registered_at` | `TIMESTAMPTZ`，非空 | 平台建立订单记录的时间，不替代事务已提交的确认 |
| 本地确认时间 | `confirmed_at` | `TIMESTAMPTZ`，条件可空 | `UNKNOWN` 时为空；确认成功或失败时必须有值，不冒充渠道实际付款时间 |

### 唯一性与原始事实保护

1. 平台支付订单号必须唯一，负责稳定定位平台订单。
2. “接入方标识＋商城业务订单号”必须联合唯一且非空，防止为同一支付意图创建多张订单。不能只依赖平台订单号唯一。
3. 订单登记后，接入方、商城业务订单号、金额和币种不得被重复请求改写；金额或币种冲突时拒绝本次请求，原订单不变。
4. 金额不得使用二进制浮点数解释或运算，不接受小数分，也不以舍入方式修正无效金额。缺少必要信息或违反金额、币种规则的初始请求，不创建订单或产生模拟支付效果。
5. 标识格式、唯一键、结果与时间的组合限制由下文统一约定；非空约束本身不等于完整输入校验。

### 支付结果规则

| 当前结果 | 本次取得的信息 | 允许的处理 |
|----------|----------------|------------|
| 未知 | 与订单匹配的确认成功信息 | 有条件地保存已确认成功，并记录本地确认时间 |
| 未知 | 与订单匹配的确认失败信息 | 有条件地保存已确认失败，并记录本地确认时间 |
| 未知 | 查询失败、无匹配记录、仍不可确认或信息不匹配 | 保留未知，不自动重新付款；必要核实与异常信息另行记录 |
| 已确认成功或已确认失败 | 一致且匹配的确认信息 | 幂等接受，保留已有确认结论 |
| 已确认成功或已确认失败 | 故障、未知、矛盾或不匹配的信息 | 不直接覆盖原结果，写入结果处理记录保留核实情况或冲突证据 |

- 查询失败不需要把支付结果重新写成未知，也不能把付款改成失败。
- 已确认失败的订单重复提交仍返回原失败结果，首期不支持重新支付。
- 数据库中的结果取值限制不等于合法迁移保护；条件写入和短事务方案见后文，实际 SQL 与并发保证仍须实现并用真实数据库验证。

### 发起资格不是可重置开关

- 只有本次登记操作已确认新建并提交成功，当前流程才取得发起资格。
- 读到订单存在或结果未知，不产生新的发起资格；重启与重复请求也不能重新领取。
- 不增加可被反复读取、重置的“可以付款”布尔字段，也不增加 `is_paid` 重复表达三类支付结果。
- 订单已登记并不证明 Mock 已处理；Mock 交易号暂缺也不证明付款尚未发生。必须根据已有事实与渠道核实处理，不由字段空值推断需要补付。

## Mock 渠道交易

Mock 交易表达模拟渠道自己处理并保存的事实，不等于平台支付订单，也不等于中台某次付款调用或查询收到的答复。Mock 查询从自己的记录中取值，不读取平台订单结果来拼装渠道结论。

### Mock 交易信息

对应表名为 `mock_transactions`。

| 信息 | 数据库字段 | 类型与空值 | 含义与记录规则 |
|------|------------|------------|----------------|
| Mock 交易号 | `id` | `UUID`，主键 | Mock 自己生成 UUIDv4，不把平台支付订单号当成渠道交易号 |
| 平台关联编号 | `platform_reference_id` | `UUID`，非空且唯一 | 直接使用对应平台支付订单号，不另造发起编号，用于查询原交易 |
| 实际处理金额 | `amount` | `BIGINT`，非空 | 保存付款调用中实际处理的整数分金额，不在查询时从平台订单表回填 |
| 币种 | `currency` | `TEXT`，非空 | 保存 Mock 实际处理的币种，不由查询请求的期望值替换 |
| 实际交易结果 | `result` | `TEXT`，非空 | 仅取 `SUCCEEDED`、`FAILED`，不设置默认成功，不以答复是否送达决定结果 |
| Mock 处理时间 | `processed_at` | `TIMESTAMPTZ`，非空 | Mock 形成该交易结果的时间，不等于中台本地确认时间 |

### 交易事实与调用表现分离

- Mock 已保存成功但付款答复丢失时，Mock 交易仍是成功，平台可以暂时未知；后续查询核实的是同一笔交易。
- 若付款尚未形成 Mock 交易就中断，可以没有对应交易记录。平台查不到时仍保持未知，不能据此重新付款。
- 查询失败、答复丢失、结果暂时不可取得等由可信的故障场景控制，不通过把已保存的成功改成未知或失败实现。
- 延迟后可查不等于由查询触发付款；查询不能创建模拟付款效果。首期不为 Mock 交易增加后台处理或处理中状态。
- 场景切换不得改写已有交易事实。场景配置、加载与可见性控制留到运行和验证设计阶段明确。

### 唯一关联与防重

1. Mock 交易号必须唯一。
2. 平台关联编号必须有值且在 Mock 交易记录中唯一。首期同一平台支付订单至多对应一笔 Mock 交易，便于明确定位原交易。
3. 重复付款调用的关联编号、金额和币种一致时，复用原交易，不生成新交易，也不改写原结果与处理时间。
4. 同一关联编号携带不同金额或币种时，拒绝本次调用，不覆盖原记录，也不产生新的模拟付款效果。拒绝本次冲突调用不等于把原交易改成失败。
5. 这只是 Mock 自身的防线，不改变中台必须至多发起一次付款的要求；不得据此为未知订单重新付款。

### 调用次数与模拟效果分别验证

- Mock 交易表只有一条记录，不能证明中台只发起过一次付款；防重可能已经挡住重复调用。
- 测试必须单独观测中台发起付款的次数，以及 Mock 实际产生的模拟付款效果，不能仅以交易表行数推断前者。
- 调用次数的观测不能只发生在成功新增交易时，否则被防重拦下的调用会被漏计。
- 付款调用次数的独立观测与持久化方式留待验证专题落实，不以结果处理记录替代；本轮不增加调用计数表或相关字段。

## 结果处理记录

使用追加式记录解释“取得了什么信息、为什么接受或拒绝”，同时覆盖首次付款答复与后续查询核实。记录关联已有平台支付订单，不是支付尝试，也不是另一套订单状态或事件溯源系统。

### 记录信息

对应表名为 `result_handling_records`。八类逻辑信息映射为十一列；不增加新的业务实体。

| 信息 | 数据库字段 | 类型与空值 | 含义与记录规则 |
|------|------------|------------|----------------|
| 记录编号 | `id` | `UUID`，主键 | 应用生成 UUIDv4；同次观测的保存重试复用编号，不重新付款 |
| 平台支付订单号 | `payment_order_id` | `UUID`，非空 | 引用已有平台订单，不为追踪创建支付或空订单 |
| 请求编号 | `request_id` | `UUID`，非空 | 由入口为本次请求生成 UUIDv4，不承担支付意图识别或付款资格判断 |
| 来源 | `source` | `TEXT`，非空 | `PAYMENT` 表示首次付款调用的答复或故障，`QUERY` 表示后续核实 |
| 观测时间 | `observed_at` | `TIMESTAMPTZ`，非空 | 本地取得答复或发现故障的时间，不冒充渠道实际处理时间 |
| 核实依据 | `evidence` | `JSONB`，非空且为对象 | 仅保存下文允许字段；无答复时可显式记录空对象并说明原因，不补造渠道结果 |
| 处理前后结果及决定 | `result_before`、`result_after`、`decision` | 三列均为非空 `TEXT` | 前后结果取平台三类值；处理决定见下文，不用调用 Mock 前的旧快照拼装 |
| 异常原因 | `reason_code`、`reason_message` | 两列均为可空 `TEXT` | 分类码最长64字符，脱敏说明最长512字符；无异常时可空，有异常时必须提供原因分类，不整包保存原始错误或报文 |

### 记录范围

- 首次付款答复或调用故障被处理时，记录取得的信息及处理决定。
- 对未知订单实际进行查询核实时，包括查询失败、无匹配记录、仍不可确认、错配或冲突，都应记录结论和原因，不因订单结果未改变而省略。
- 普通查询已确认订单，若只是读取已有结果，不必每次新增业务核实记录，访问日志即可；实际发生后续核实时仍遵守上述记录规则。
- 无对应平台订单的请求不为此创建支付或空订单；入口及无记录查询的必要排查信息由受控日志记录。
- 不以不断覆盖的“最后错误”字段代替核实历史，也不通过重放处理记录重新驱动付款。

### 确认结果与依据的保存边界

1. 新接受的确认结果与支撑该结论的最小结果处理记录，必须在同一平台数据库事务中保存；记录中的前后结果和决定应与实际条件写入一致。Mock 自身交易提交仍独立。
2. 若不能确认上述事务已提交，不宣称新结论已可靠记录。提交结果不明时，读回订单及同次处理记录核对，不直接假定回滚，也不重新付款。
3. 查询故障、无匹配、错配等不推进支付结果的分支，也必须正常保存处理记录；不能把记录降成可选装饰，或仅靠打印日志宣称正常追踪已完成。
4. 已经能够读取的确认结果，不以额外追踪写入成功为返回前提，不能因该写入失败而降级或改成付款失败。这不承诺数据库本身不可读时仍然可以查单。

### 追踪保存失败的显式限制

- 数据库无法写入记录时，明确报告本次追踪保存失败，留下可按业务标识和请求编号定位的脱敏运行日志，不声称记录已经落库。
- 保存失败必须作为可观察的处理故障，不能吞掉后宣称该次核实与追踪完全成功；不能将它当成追踪验收通过。
- 运行日志不是确认结果与依据已提交的证明。日志的留存、检索和故障场景验证须在验证阶段落实，不能只凭“打印过”宣称满足完整追踪要求。
- 首期不增加可靠审计补偿队列，不承诺异常历史绝无缺口、数据库恢复后自动补齐。该限制不豁免正常路径保存核实记录及对故障留痕的要求，也不允许重付或改写已有确认事实。

### 保存重试与次数观测

- 同一次观测的保存重试复用记录编号；真正再次查询核实应生成另一条记录，即使属于同一订单、同一外层请求或得到相同结果。
- 不按订单号或客户端请求号粗略去重。已存在同编号记录时必须核对关联与语义，复用一致的既有处理决定，不能吞掉重复键错误后继续盲目修改订单。
- 结果处理记录混有查询，调用也可能在答复或记录保存前中断，保存重试又可能被去重，因此记录数量不能证明付款调用次数。
- 付款发起次数仍需独立观测，包括被 Mock 防重挡住、超时和失败的调用；具体方式在验证专题落实，不新增付款任务系统。

## 通用存储约定

### 编号、文本与时间

- 三张表各自的主键和入口请求编号采用应用生成的 UUIDv4，数据库用 `UUID`。各编号职责独立；Mock 的平台关联编号直接引用平台订单号的值，不再生成额外支付意图编号。
- 编号在需要使用之前生成；同次结果保存重试保留记录号。生成 UUID 不代替主键与唯一约束，随机碰撞等其他唯一错误不能冒充意图重复。
- `client_id`、`business_order_no` 均为1～64个 ASCII 英文字母、数字、短横线或下划线，按原值区分大小写。拒绝空串、空格和其他字符，不截断、不自动裁剪或转小写；数据库比较规则必须区分大小写。
- `reason_code` 有值时长度为1～64字符，使用稳定分类；`reason_message` 最长512字符，仅保存脱敏摘要。字符数不是 UTF-8 字节数，校验与数据库长度约束应一致。
- 所有时间列使用 `TIMESTAMPTZ`，应用和数据库会话统一 UTC。该类型保存时间点，不保留原输入时区；输出不能仅因使用此类型就假定已按 UTC 显示。
- 登记、渠道处理、本地确认和观测时间分别保留各自含义；不能依靠时间戳的新旧覆盖确认结果，也不承诺跨模块时钟严格有序。

### 结果、处理决定与证据

- 结果、来源和处理决定均采用 `TEXT` 加合法取值 `CHECK`，首期不使用数据库自定义枚举。这里的编码只约束内部存储，不预先确定对外 API 表达。
- 平台金额检查为1～1,000,000分，币种检查为 CNY；Mock 保存自身处理值，不能通过读取平台表补成“匹配”的结果。
- 平台 `result = UNKNOWN` 时 `confirmed_at` 必须为空；`SUCCEEDED` 或 `FAILED` 时必须非空。该组合检查仍不能代替迁移规则和条件写入。

| 处理决定编码 | 含义与状态组合 |
|--------------|----------------|
| `ACCEPT_CONFIRMATION` | 接受匹配确认；之前为 `UNKNOWN`，之后为 `SUCCEEDED` 或 `FAILED` |
| `KEEP_UNKNOWN` | 仍无法确认；前后均为 `UNKNOWN`，原因说明无匹配、查询故障等情况 |
| `KEEP_CONFIRMED` | 保留已确认结果；前后是相同的 `SUCCEEDED` 或 `FAILED` |
| `REJECT_EVIDENCE` | 拒绝错配、冲突或无效信息；结果不变，必须说明异常原因 |

- `evidence` 只允许 `platform_reference_id`、`mock_transaction_id`、`amount`、`currency`、`result`、`differences`。前五项保存取得的必要信息，`differences` 只列出不匹配的字段名，不是任意嵌套报文。
- 值的类型、长度或格式不合法时记录字段错误分类，不把未经筛选的原始内容直接塞进证据，也不接纳无界字符串或任意嵌套内容。金额保持整数语义，不经浮点转换；未取得的字段不补造。
- 接受新确认时必须保存足以核对原订单的关联、金额、币种和确认结果，不能用空对象代替最小依据；取得的交易号也必须按业务关联规则核对。
- 数据库检查 `evidence` 是 JSON 对象，应用负责允许字段、类型与脱敏校验。`JSONB` 本身不提供这些业务保证。

## 关联、唯一键与索引

| 表或关联 | 约定 |
|----------|------|
| `payment_orders` | `id` 为主键；`client_id` 与 `business_order_no` 联合唯一且非空 |
| 平台已关联的 Mock 交易号 | `mock_transaction_id` 有值时唯一，可有多个空值；不能让两个订单关联同一个已知 Mock 交易号 |
| `mock_transactions` | `id` 为主键；`platform_reference_id` 唯一且非空，保证同一平台关联至多一笔 Mock 交易 |
| `result_handling_records` | `id` 为主键；同次观测重试按该编号核对，不按订单或请求号去重 |
| 订单与处理记录 | `payment_order_id` 外键引用 `payment_orders.id`，删除采用 `RESTRICT`，不级联抹掉证据 |
| 订单与 Mock | 按平台编号及交易信息逻辑关联；两端不建立跨模块外键，也不对证据中的渠道编号设置外键 |

- 不设 Mock 跨模块外键，是避免模拟渠道依赖平台表生命周期的取舍；外键本身并不要求共用事务。无外键不免除中台在调用前确认登记、接收结果时核对关联的责任。
- 主键与唯一约束已提供相应索引，不重复创建。另为处理记录安排 `(payment_order_id, observed_at, id)` 索引，支持按订单查看历史；不提前建设额外统计索引。
- 应用不提供删除或重置支付记录的能力，也不通过通用整单保存改写身份、金额和币种。测试清理只在明确隔离的环境执行。
- 原始事实不可改写、记录追加式保存由业务约定和专用 SQL 实现；不声称取值检查能够阻止所有错误更新，首期不使用触发器隐藏付款流程。

## 短事务与并发方案

初期明确使用读已提交（`Read Committed`），结合唯一键、条件写入与必要的单订单短行锁，不靠提高隔离级别代替业务规则。

### A. 登记支付意图

1. 入口已确认接入方身份，支付业务完成业务输入校验；数据访问操作准备候选订单号，开始短事务。
2. 针对“接入方＋商城业务订单号”的唯一键尝试插入，采用 `ON CONFLICT DO NOTHING`，预期冲突不修改原记录。不能把所有唯一约束错误都归为业务重复。
3. 本次确实新建时，只有事务提交得到确认，才返回“本次新建且已提交”及发起资格。其他流程不能从已存在行或未知状态重新领取资格。
4. 因业务键冲突未插入时，用下一条独立查询读取已有订单，再由业务比较金额和币种。读已提交下，不保证同一条插入语句的快照能看到并发冲突行，故不强求用一条 CTE 包办所有分支。
5. 若仍无法可靠读取或不能确认提交，报告无法确认，不直接当成无记录，不调用 Mock。即使稍后查到行，也不能反推本次流程重新取得发起资格。

Mock 付款调用只发生在这段事务结束且资格明确之后；不跨渠道调用持有平台事务或订单行锁。

### B. 保存确认或核实结论

1. 先在事务外完成 Mock 调用及信息校验，固定本次观测、记录编号和允许的依据，不在保存重试中重新调用付款。
2. 开始短事务，按记录号检查是否已经处理。命中时核对订单、请求、来源、观测时间和依据等不变事实；一致才复用原决定，异义同号必须拒绝。
3. 尚未处理时，按稳定订单号及接入方范围用 `SELECT FOR UPDATE` 锁住这一笔订单并读取当前状态。不能用“仍为未知”作为锁定行的过滤条件，否则等待期间已确认的订单可能被误判为不存在。锁后可以再次检查记录号，减少同次并发保存的重复冲突。
4. 根据锁保护下的实际状态接受确认或保持原结论。接受新确认仍使用明确条件更新，只改允许的结果、确认时间及已校验关联信息，不改原始付款事实；查询故障或错配不把结果写回未知。
5. 写入同一事务中的结果处理记录。其前后状态是本次行锁保护下的实际处理状态，不照抄查询 Mock 前的快照，也不承诺该历史快照永远是订单最新状态。
6. 确认提交后才认定本次保存完成。记录保存失败不能留下半套新确认；提交结果不明则读回核对，不假定回滚，也不重新付款。

行锁仅用于取得 Mock 信息之后、实际保存处理记录的短事务，目的是让包括“没有状态更新”的分支也能准确记录前后状态。普通读取已确认订单不加该锁，不新增核实记录；锁不跨越 Mock 调用或整个 HTTP 请求，锁等待和数据库操作均受既定时间预算限制。

### C. 重复记录号、故障与返回语义

- 若并发保存出现未处理的处理记录主键冲突，整段回滚后再读取已提交的同编号记录。只对这一明确冲突核对重试是否完成，其他唯一错误或数据库故障不能冒充重复成功。
- 已失败的数据库事务中不能吞掉错误后继续更新。读不到原记录或无法核对语义时，不能宣称已完成；若允许再次保存，只重试同次观测的保存步骤并复用记录号。
- 重试核对不要求重新推导的前后状态等于历史记录；历史处理决定保持不变。对外需要订单当前结果时，另行可靠读取，不能把旧记录中的 `UNKNOWN` 当作当前结果，覆盖后来已保存的确认。
- 查询故障等不更新结果的分支同样按 B 保存记录；若记录写入不可用，遵守前述显式失败与脱敏日志边界，不阻断已经能够读取的确认结果，不引入审计补偿系统。
