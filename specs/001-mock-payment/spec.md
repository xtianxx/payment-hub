# Feature Specification: 模拟商城一次性 Mock 支付闭环

**Feature Branch**: `001-mock-payment`

**Created**: 2026-11-05

**Status**: Approved（2026-11-05 已确认首期需求基线，尚未实现）

**Input**: User description: "首期交付一个模拟商城、单接入方的普通订单一次性 Mock 支付闭环：一个商城业务订单一次性全额付款，仅 CNY，金额以整数“分”表达，具体上下限在需求阶段确定；接入方提交支付后可查询获取结果；同一业务意图复用已有支付订单，相同请求返回已有结果，金额或币种冲突明确拒绝且不覆盖原记录；首期不创建多次支付尝试、不自动切换渠道，明确失败后暂不支持重新支付；渠道回调与 Payment Hub 向接入方发送通知后置。超时或结果未知不得等同于成功或确定失败，须保留未知并支持后续查询核实；已有确认结果遇到查询失败不得降级或覆盖。先明确用例、非目标与验收，再进行技术设计。"

## Clarifications

### Session 2026-11-05

- Q: 首期支付意图的唯一业务标识是什么？ → A: 使用“接入方标识＋商城业务订单号”；同一组合仅关联一个支付订单，不另要求独立支付意图编号。
- Q: CNY 整数分金额的有效范围是什么？ → A: 1 至 1,000,000 分，两端包含（0.01 至 10,000 元）；仅为模拟商城演示业务限额，不宣称渠道或监管限额。
- Q: 服务重启后订单与幂等保障是什么？ → A: 重启后仍须能查询已登记订单，相同支付意图复用原订单，不因重启产生第二次支付；具体存储/恢复技术留待后续设计。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 提交一次性支付并确认成功或确定失败 (Priority: P1)

接入方为模拟商城的普通订单发起一次性全额付款。Payment Hub 为有效请求创建一个平台支付订单，并至多向 Mock 渠道发起一次模拟支付处理；当 Mock 给出明确结果时，接入方随后查询可得到已确认的成功或确定失败结果。成功结果必须与商城业务订单、金额和币种正确关联；确定失败必须被如实保留，不能被当作成功或未知。

**Why this priority**: 这是首期最小可演示闭环：没有“提交—查询—得到可解释结果”，后续幂等与未知核实都失去业务落点；本故事中的金额、币种和结果语义是首期必需的正确性要求，与其余 P1 故事共同构成完整闭环。

**Independent Test**: 使用预置的有效商城业务订单和可控 Mock 夹具，分别构造明确成功与明确失败；提交一次支付并查询，检查支付订单数量、模拟支付效果数量、结果类别及订单关联。无需依赖其他用户故事。

**Acceptance Scenarios**:

1. **Given** 接入方存在有效的商城业务订单，请求使用 CNY 整数分金额且币种为 CNY，且 Mock 已设为明确成功或明确失败，**When** 首次提交支付并随后查询，**Then** 平台创建恰好 1 个支付订单，产生至多 1 次模拟支付效果，查询确认与 Mock 设置相对应的已确认成功或已确认失败结果。
2. **Given** 首次提交已得到确认成功，**When** 接入方按同一支付意图查询，**Then** 返回该支付订单的确认成功结果，金额、币种和商城业务订单关联与提交时一致。
3. **Given** 首次提交已得到确定失败，**When** 接入方查询，**Then** 返回确定失败，不伪装为成功或未知，也不自动发起第二次支付。
4. **Given** 请求缺少必要的业务关联信息、币种不是 CNY，或金额不是有效的整数分表达，**When** 提交支付，**Then** 平台拒绝请求，不创建支付订单，也不产生任何模拟支付效果。
5. **Given** 已登记且已确认成功或确定失败的支付订单，**When** 服务重启后按同一支付意图查询，**Then** 返回同一订单标识、金额、币种和商城业务订单关联，已确认结果保持不变。

### User Story 2 - 同一支付意图的重复、并发与冲突处理 (Priority: P1)

接入方可能因网络重试、页面重复操作或并发调用，对同一支付意图提交多次相同请求；也可能提交金额或币种不同的冲突请求。平台应复用已有支付订单并返回其已有结果，不产生重复支付效果；对冲突请求应明确拒绝，且不得修改原记录。若已有确定失败，重复相同请求只返回原失败结果，首期不支持重新支付。

**Why this priority**: 幂等与冲突处理直接决定会不会重复扣款或静默改写订单，属于首期支付安全规则；缺少它会使重复请求产生重复业务效果或覆盖原订单，因此与正常提交同为 P1 必需能力。

**Independent Test**: 预置一个已有成功结果和一个已有确定失败结果的支付订单，分别顺序重放两次、并发提交两次、提交金额或币种冲突请求；观察支付订单数、模拟支付效果数以及原订单字段是否保持不变。

**Acceptance Scenarios**:

1. **Given** 同一支付意图已有支付订单及其结果，**When** 以完全相同请求顺序重复提交 2 次，**Then** 每次返回同一支付订单及其已有结果，支付订单数与模拟支付效果数均不增加。
2. **Given** 同一支付意图尚无支付订单，**When** 两个相同的有效请求并发提交，**Then** 最终恰好产生 1 个支付订单和至多 1 次模拟支付效果，两个请求均关联该支付订单，后续查询所得结果一致，不增加重复业务效果；不要求两个请求在各自处理时刻返回相同的状态快照。
3. **Given** 同一支付意图已有支付订单，**When** 提交金额或币种不同的请求，**Then** 平台明确拒绝为冲突，不修改原订单的金额、币种和结果，也不创建新的支付订单或模拟支付效果。
4. **Given** 同一支付意图已有确定失败结果，**When** 接入方重复提交相同请求，**Then** 返回既有失败结果，首期不发起新的支付尝试；如接入方要求重新支付，平台明确表示暂不支持。
5. **Given** 已登记且已有确认成功或确定失败结果的支付订单，**When** 服务重启后重复提交相同请求，**Then** 返回原订单及原结果，不生成新支付订单或新模拟支付效果；若原结果为确定失败，不重新支付。

### User Story 3 - 超时或结果未知后的查询核实 (Priority: P1)

提交支付时，Mock 可能超时、通信失败或返回无法确定的结果。平台必须把这类情形保留为“未知”，不能猜成成功或确定失败。接入方查询时，平台对仍未知的支付订单向 Mock 核实；核实得到匹配的确认结果才更新，仍无法确认则继续未知。已有确认结果时，读取该结果不以再次向 Mock 查询成功为前提；若后续核实遇到查询故障，不得降级或覆盖原结果，只记录查询失败。查询无对应平台订单时应明确“无记录”；平台订单存在但 Mock 无匹配结果时不得自动重发。

**Why this priority**: 未知结果的语义是支付正确性的核心，也是本闭环区别于“接口返回成功即可”的关键验收；超时不等于失败或成功，必须与成功、失败路径同时交付并独立验证，不能后置。

**Independent Test**: 使用可控 Mock 分别产生超时、延迟后可查、查询失败和无匹配记录；对未知订单和已确认订单发起查询，检查结果类别、是否发生自动重发、查询失败记录以及“无记录”返回。

**Acceptance Scenarios**:

1. **Given** 首次提交时 Mock 超时或结果无法确定，**When** 提交处理结束，**Then** 平台支付订单保留“未知”结果，不标记为成功或确定失败。
2. **Given** 支付订单结果为未知，**When** 接入方查询且 Mock 核实返回与订单匹配的确认结果，**Then** 平台返回该确认结果，并保持与商城业务订单、金额和币种的正确关联。
3. **Given** 支付订单结果为未知，**When** 接入方查询但 Mock 核实仍无法确认，**Then** 结果继续保持未知，不猜测成功或失败，也不自动重发支付。
4. **Given** 支付订单已有确认成功或确定失败结果，**When** 发生后续核实且遇到 Mock 查询故障，**Then** 平台仍可读取并保留已有确认结果，不降级、不覆盖，仅记录本次查询失败。
5. **Given** 不存在对应平台支付订单，**When** 接入方查询，**Then** 平台明确返回“无记录”，不伪装为支付失败，不创建支付订单，也不产生模拟支付效果。
6. **Given** 支付订单结果仍为未知，平台支付订单存在但 Mock 无匹配交易或结果，**When** 平台查询核实，**Then** 不自动重发支付，保留未知待核实，并给出可观察的待核实状态。
7. **Given** 已登记且结果为未知的支付订单，**When** 服务重启后查询且 Mock 仍无法确认结果，**Then** 原订单继续保持未知，不因重启变为已确认成功或已确认失败；若后续查询取得匹配的 Mock 确认结果，则返回该确认结果，不产生新的支付效果。

---

### Edge Cases

- 金额边界：1 分和 1,000,000 分（含两端，即 0.01 至 10,000 元）在其余请求条件有效且 Mock 设置明确时应被接受；0 分、-1 分、1,000,001 分、0.5 分等非整数分以及非 CNY 请求应被拒绝，且不产生支付订单或模拟支付效果。0.01 元以 1 分表示时合法，不应因“元”形式的小数而误判。
- 支付意图唯一标识为“接入方标识＋商城业务订单号”；同一组合仅关联一个支付订单，不同组合属于不同支付意图。不得通过新造独立支付意图编号绕过同一商城订单的唯一订单约束；确定失败后的相同请求仍返回原失败结果。
- 同一支付意图的重复提交与金额/币种冲突同时发生：重复提交不得新增效果，冲突部分必须被拒绝，原订单保持不变。
- 支付结果为未知期间接入方重复提交：复用原支付订单，不新增支付尝试，结果仍为未知。
- Mock 返回的渠道交易标识、业务关联标识、金额或币种与平台支付订单不匹配：不得据此更新结果，保留原结果或未知，并留下可观察的异常记录。
- 查询请求缺少定位字段或格式无效：明确拒绝；定位信息合法但不存在对应订单：返回“无记录”；请求不属于唯一模拟商城演示上下文：不返回订单信息，不改变任何订单。
- 支付订单结果仍为未知、平台支付订单存在但 Mock 无匹配记录：保持未知待核实，不自动重发，也不改写为失败。
- 服务重启以已登记订单为前提：已确认成功、已确认失败和未知订单在重启后仍保持同一订单标识、金额、币种和业务关联；已确认结果保持，未知不因重启变为成功或失败；相同支付意图重放不生成新订单或新支付效果。不扩展到磁盘损坏、数据中心容灾或真实渠道事务实现。
- 查询核实长时间没有结论：保持未知，不因时间流逝自动转为成功或失败。

## Requirements *(mandatory)*

### 已确认范围与非目标

**已确认范围**：单个演示接入方、单 Mock 渠道的模拟商城普通订单一次性全额支付；支付意图唯一标识为“接入方标识＋商城业务订单号”，同一组合仅关联一个平台支付订单，不另要求独立支付意图编号；仅 CNY，金额以整数“分”表达，有效范围为 1 至 1,000,000 分（两端包含，即 0.01 至 10,000 元）；接入方提交支付后可查询获取结果；同一支付意图复用已有支付订单，重复或并发请求不产生额外支付效果，金额或币种冲突明确拒绝且不覆盖原记录；超时或结果未知保留为未知，并支持查询向 Mock 核实；服务重启后已登记订单仍可查询，相同支付意图复用原订单，不因重启产生第二次支付。首期不创建多次支付尝试，不自动切换渠道，明确失败后暂不支持重新支付；渠道回调与向接入方通知后置。

**非目标**：

- 不开发完整商城：商品、库存、履约仍为外部业务场景或测试夹具，不意味着本期交付真实商城应用。
- 不接入真实支付、不处理真实资金、不提供真实收银页或付款人交互。
- 不做退款。
- 不做多渠道、渠道自动切换或多渠道路由。
- 不做渠道回调，也不向接入方发送商户通知。
- 不做商户入驻、多租户管理、分账、钱包、资金结算、账单或交易对账。
- 不做完整运营后台，不承诺生产级 SLA、高可用或规模指标。
- 本期是纯 Mock 测试边界，不宣称生产鉴权、安全或合规已就绪，也不强制任何身份技术机制。

### Functional Requirements

- **FR-001**: 接入方提交支付时，平台必须接收足以定位支付意图和关联商城业务订单的信息，包括接入方标识、商城业务订单号、CNY 整数分金额和币种，并将支付订单与接入方及商城业务订单建立关联。支付意图的唯一业务标识为“接入方标识＋商城业务订单号”；同一组合仅关联一个平台支付订单，不另要求独立支付意图编号。
- **FR-002**: 平台必须仅接受 CNY，金额必须用整数“分”表达；有效范围为 1 至 1,000,000 分，两端包含（即 0.01 至 10,000 元），该范围仅为模拟商城演示业务限额，不宣称渠道或监管限额。1 分（0.01 元）是合法表示；不得接受非整数的分金额，也不得将小数分舍入为整数分；不得使用二进制浮点数进行金额解释或运算。金额为 0 分、负数（如 -1 分）或高于 1,000,000 分（如 1,000,001 分）的请求必须拒绝；币种不是 CNY 的请求必须拒绝。
- **FR-003**: 对一个新且有效的支付意图，平台必须创建恰好 1 个支付订单，并至多向 Mock 发起 1 次模拟支付处理；首期不得为同一支付意图创建第二次支付尝试，不得自动切换渠道。
- **FR-004**: 支付结果必须区分为“已确认成功”“已确认失败”和“未知”三类。尚未取得确认结果时，超时、通信失败或无法取得确定响应必须保留为未知，不得直接视为成功或确定失败；只有 Mock 明确返回且与平台支付订单匹配的结果，才可记为确认结果。已有确认结果时发生查询或通信故障，必须按 FR-007 保留原结果，不得退回未知。
- **FR-005**: 接入方必须能够按支付意图查询平台支付订单及其已有结果。查询与提交是不同业务动作；查询本身不得创建支付、不得改变支付意图，也不得触发新的支付尝试。
- **FR-006**: 当支付订单结果仍为未知时，查询必须向 Mock 核实。核实返回与订单匹配的确认结果时，平台可将其记录为确认结果；核实仍无法确认时，结果必须继续保持未知，且不得自动重发支付。当支付订单结果仍为未知、且平台支付订单存在但 Mock 无匹配结果时，同样保留未知待核实，不得自动重发。
- **FR-007**: 当支付订单已有确认成功或确定失败结果时，读取并返回该已有确认结果，不以再次向 Mock 查询成功为前提；若发生后续核实且遇到 Mock 查询故障，不得降级、覆盖或改写已有结果，平台必须保留原确认结果，仅记录本次查询失败。
- **FR-008**: 当不存在对应平台支付订单时，查询必须明确返回“无记录”；不得伪装为支付失败，不得创建支付订单，也不得产生模拟支付效果。
- **FR-009**: 同一支付意图的顺序重复或并发重复请求必须复用同一支付订单，至多产生 1 个支付订单和 1 次模拟支付效果，并返回该订单及其当前已有结果。重放不得要求永久冻结首次同步响应；后续查询可以确认原先未知的结果。
- **FR-010**: 同一支付意图下，金额或币种与已有支付订单不一致的请求必须被明确拒绝为冲突；平台不得修改原订单的金额、币种或结果，不得创建新支付订单，也不得产生新的模拟支付效果，不得静默合并或覆盖。
- **FR-011**: 当支付订单已有确定失败结果时，相同请求的重复提交必须返回既有失败结果，不得自动重试或发起新的支付尝试。首期不支持明确失败后的重新支付；接入方要求重新支付时，平台必须明确告知暂不支持。
- **FR-012**: 平台必须校验 Mock 返回的交易或结果与平台支付订单的业务关联标识、金额和币种是否匹配。任一不匹配时，不得据此更新订单结果；必须保留原结果或未知，并记录可观察的不匹配异常，不得把不匹配结果当作成功或失败。
- **FR-013**: 提交前校验失败的初始无效请求不得创建支付订单、不得产生模拟支付效果，也不得占用或改变既有支付意图的结果。
- **FR-014**: 平台必须仅在唯一模拟商城的演示上下文中定位支付订单；查询请求缺少定位字段或格式无效时必须明确拒绝，定位信息合法但不存在对应订单时必须返回“无记录”，不属于该演示上下文的请求不得读取、复用、覆盖或返回该上下文之外的订单信息。
- **FR-015**: 平台必须记录足以按业务标识定位支付订单、结果变化、查询核实结论和失败原因的最小业务追踪信息；不得记录真实凭据、支付敏感信息或未经脱敏的个人数据，演示数据不得包含真实支付信息。
- **FR-016**: 服务重启后，平台必须仍能按支付意图查询已登记订单，并复用原支付订单，不因重启产生第二次支付。已登记订单指平台已创建并记录的支付订单。对已确认成功、已确认失败和未知三类已登记订单，重启后必须保留同一订单标识、金额、币种和业务关联；已确认结果不得因重启改变，未知不得因重启变为已确认成功或已确认失败；未知订单后续查询仍可向 Mock 核实为匹配的确认结果，或继续保留未知；相同支付意图的重放不得生成新支付订单或新模拟支付效果，已确认失败后的相同请求仍返回原失败结果且不重付。具体存储和恢复技术留待后续设计；本保障以已登记订单为前提，不扩展到磁盘损坏、数据中心容灾或真实渠道事务实现。

### Key Entities *(include if feature involves data)*

- **接入方商城业务订单**：接入方为商品或服务建立并管理的一次性付款业务单据，承载商品、服务和履约等业务含义。它是支付意图关联的外部业务对象，不由本平台创建或履约。首期按一次性付款范围，支付意图唯一标识为“接入方标识＋商城业务订单号”；同一组合仅关联一个平台支付订单，一个商城业务订单至多关联一个平台支付订单，不另要求独立支付意图编号。
- **平台支付订单**：Payment Hub 侧表达并跟踪一项支付业务意图的业务概念，与接入方及商城业务订单关联。它承载金额（CNY 整数分，1 至 1,000,000 分）、币种、结果类别（已确认成功、已确认失败、未知）、查询核实状态和必要业务追踪信息；作为已登记订单，在服务重启后仍保持同一订单标识、金额、币种和业务关联；不等于支付尝试、渠道交易或单次请求。
- **Mock 渠道交易/结果**：Mock Provider 对一次模拟支付处理的渠道侧记录与返回，包含渠道侧交易标识、业务关联信息、金额、币种、结果或不可确定状态。它与平台支付订单通过业务关联联系，但标识和语义由 Mock 渠道定义；Mock 可受控产生成功、确定失败、超时、延迟后可查、查询失败及不匹配结果。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在预置有效商城业务订单下，首次有效提交产生恰好 1 个平台支付订单，模拟支付效果不超过 1 次，且结果可被查询为已确认成功、已确认失败或未知之一。
- **SC-002**: 对同一支付意图顺序重复提交 2 次，支付订单数不增加、模拟支付效果数不增加，且每次返回同一支付订单及其已有结果。
- **SC-003**: 从一个尚无支付订单的有效支付意图出发，并发提交 2 个相同请求，最终恰好产生 1 个支付订单和至多 1 次模拟支付效果，两个请求均关联该支付订单；最终查询所得结果一致，且不出现重复业务效果。
- **SC-004**: 初始无效请求（含缺少业务关联信息、币种非 CNY、非整数分金额、金额为 0 或负数、金额高于 1,000,000 分）产生 0 个新增支付订单和 0 次模拟支付效果。
- **SC-005**: 金额或币种冲突请求产生 0 个新增支付订单和 0 次新增模拟支付效果，且原支付订单的金额、币种和结果均保持不变。
- **SC-006**: 成功、确定失败、未知、核实后确认、核实仍未知、已有确认结果遇到查询失败、查询无记录、原结果未知且平台订单存在但 Mock 无匹配结果，均能通过查询或业务追踪得到可区分且可观察的结果；未知不得被计入成功或失败。
- **SC-007**: 对已有确定失败的支付意图重复提交相同请求，新增支付尝试数为 0、新增模拟支付效果数为 0，返回既有失败结果。
- **SC-008**: 对尚无支付订单且业务关联信息有效的新支付意图，1 分和 1,000,000 分在 Mock 设置明确时被接受并产生对应结果；0 分、-1 分、1,000,001 分、0.5 分等非整数分及非 CNY 请求被拒绝，且不产生支付订单或模拟支付效果；0.01 元以 1 分表示时合法。
- **SC-009**: 对任一样本支付订单，可通过业务标识定位其订单、结果变化和查询失败记录；演示数据中真实凭据、支付敏感信息和未脱敏个人数据的数量为 0。
- **SC-010**: Mock 返回业务关联标识、金额或币种不匹配时，订单结果更新次数为 0，订单保持原结果或未知，并留下可观察的不匹配异常记录。
- **SC-011**: 对已登记且已确认成功、已确认失败或未知的支付订单，服务重启后仍可按同一支付意图查询到同一订单标识、金额、币种和业务关联；已确认结果保持不变，未知不因重启变为已确认成功或已确认失败；相同支付意图重放不生成新支付订单或新模拟支付效果，确定失败重放不重付；未知订单后续查询可按 Mock 匹配结果确认或继续未知。

## Assumptions

- 单商城演示上下文：一个接入方、一个 Mock 渠道、普通订单一次性全额付款；商品、库存和履约由外部业务场景或测试夹具提供，不在本期实现。
- Mock 可受控产生成功、确定失败、超时或结果不可确定、延迟后结果可查、查询失败、无匹配记录及冲突或不匹配信息，以支撑本期验收。
- 金额有效范围 1 至 1,000,000 分（两端包含，即 0.01 至 10,000 元）仅为模拟商城演示业务限额，不宣称渠道或监管限额。
- 真实用户认证、生产运营、真实资金处理和合规不在本轮；本期仅一个演示接入方，以演示级接入方标识定位业务数据，不预设具体身份、鉴权或多租户技术机制。
- 具体协议、接口形式、存储、消息和部署方式留待技术计划；本规格不据此锁定实现，也不把支付订单、支付尝试和技术重试视为同一概念。
- 服务重启后的业务保障已确认：以已登记订单为前提，重启后仍可查询并复用原支付订单；具体存储和恢复技术留待后续设计，不扩展到磁盘损坏、数据中心容灾或真实渠道事务实现。
- 渠道回调、向接入方发送通知、退款、多渠道、商户入驻、分账、钱包、结算和对账均为后续方向，不构成本期交付承诺。
