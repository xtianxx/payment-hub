## Summary

首期采用 Go 单体，使用 Gin 接收 HTTP 请求，通过 pgx 和显式 SQL 访问 PostgreSQL。Mock 位于应用内部，但保存独立的模拟交易记录。完整本地演示由一个 Go 应用容器、一个 PostgreSQL 容器，以及通过 HTTP 调用的轻量演示客户端组成。

首期业务范围仍以已批准规格为准：单接入方、单 Mock、普通订单一次性付款，无真实资金。相同支付意图复用订单，冲突请求不改写原记录；未知结果通过后续查询核实，不自动重新付款。

|------|------------|--------------|
| HTTP 入口：`internal/httpapi/` | 验证业务身份、解析请求、入口保护、调用支付业务并转换答复，提供最小就绪检查 | 不直接操作支付订单表、调用 Mock 或决定付款结果 |
| 支付业务：`internal/payment/` | 提交与查询规则、重复与冲突判断、结果校验及流程编排 | 不依赖 Gin、pgx 的专用对象，不自行创建数据库连接池 |
| 平台订单存储：`internal/postgres/` | 使用 pgx 和显式 SQL 兑现约定的原子操作、查询与条件保存 | 不调用 Mock，不自行发明业务规则 |
| Mock：`internal/mock/` | 模拟付款、保存独立交易、查询原交易及受控故障 | 不修改平台支付订单，不靠读取平台结果假装查询渠道 |
| 启动组装：`internal/app/` | 检查配置与依赖，手工连接模块，管理就绪、退出和资源释放 | 不隐式执行迁移，不扫描未知订单重新付款 |

### 依赖方向与小接口

- `cmd/payment-hub` 依赖 `internal/app` 负责启动，不承载支付规则；`app` 创建连接池并手工连接各模块。
- `httpapi` 依赖 `payment`，将 HTTP 输入转换为业务参数并转换答复；`postgres` 和 `mock` 依赖 `payment` 中约定的数据类型，实现支付业务消费的小接口。
- `payment` 不反向导入 Gin、pgx、具体 Mock 或 PostgreSQL 实现，使支付规则测试不必先启动 HTTP，也不因入口或 SQL 调整改变付款资格规则。
- `postgres` 封装完整原子动作，不把新确认与最小依据拆成调用者随意拼接的 CRUD；业务接口不暴露 `pgx.Tx`、连接或原始 SQL，锁与提交细节留在存储实现中，业务规则仍沿用已确认设计。
- `mock` 使用自己的 SQL 保存和查询 `mock_transactions`，可以共用连接池但不能借用平台订单事务，也不能读取平台结果冒充渠道事实。
- 测试父进程、观察器及场景编排放在 `tests/`；应用内只保留必要且默认关闭的测试接缝，不导入测试父进程代码，不新增控制接口。
- 不建立 `pkg/` 公共 SDK、通用 `utils` 大杂烩或层层转发的 `controller/service/manager`；只在真实依赖替换或故障控制需要的位置定义小接口，不为每个结构体配接口。

设计依据：[Go 项目组织建议](https://go.dev/doc/modules/layout)。这不是 Go 强制的通用分层标准，也不新增框架、Go module 或常驻服务。

### 运行组成

- **Go 应用容器**：承载上述内部模块。配置、连接池及模块对象按应用生命周期管理；每次请求的数据与事务各自独立。
- **PostgreSQL 容器**：保存平台与 Mock 各自的记录；可以共用实例和连接池，但不能共用付款事务。更新应用不得删除数据库数据。
- **轻量演示客户端**：在本地通过真实 HTTP 入口提交、查询及重放请求，不额外建设商城服务或页面。
- **数据库迁移**：goose 是明确执行的独立步骤，不是第三个必须常驻的业务进程，也不由应用启动时偷偷改表。
- **访问范围**：首期为本地受控演示。数据库不作为公网服务开放；以后若公开部署，再补充 HTTPS 入口及相应访问限制，不将公网部署算成本轮已完成能力。

### 核心编排约束

1. 先以短的本地原子操作登记支付意图；只有本次新建且登记已确认提交，当前流程才取得发起资格。读取到未知订单不等于重新获得资格。
2. 本地登记完成后，在该事务之外调用 Mock。Mock 保存自身交易，不与平台结果保存合成一个事务。
3. 取得匹配的确认结果后，有条件地可靠保存；已确认结果不得被迟到、冲突或故障信息直接覆盖。
4. 查询已有确认结果不依赖再次向 Mock 查询成功。未知订单通过查询核实原交易；Mock 无匹配记录也不能触发重新付款。
5. 各操作有明确期限；已取得可靠结果的必要保存工作有有限收尾安排，并纳入应用退出管理，不采用无人管理的后台付款任务。

### 本轮接受的限制

- 同进程 Mock 能验证故障窗口的业务处理，但不代表真实渠道网络、独立进程故障域或真实资金事务已经验证。
- 不增加后台扫描、自动补付或重启后自动续跑全部未完成付款的承诺。
- 本地演示不提供生产高可用、磁盘损坏零丢失或公网持续可访问保证。
- 简化架构不降低金额、幂等、结果保护和真实数据库验证要求。当前数据模型、关键约束及接口合同已有设计；具体建表留到实现阶段，可执行验证步骤仍待第 4 阶段收敛。

## 本地运行、就绪与环境隔离

### 演示组成与访问范围

- Go 应用和 PostgreSQL 仍是两个常驻容器。应用默认只向宿主机发布 `127.0.0.1:8080`，端口可配置；容器内应用可监听 `0.0.0.0`，不能因此将宿主机发布地址也放宽到所有网卡。
- 演示 PostgreSQL 使用持久化命名卷，不向宿主机发布数据库端口；应用通过 Compose 网络中的数据库服务名访问它。
- goose 作为明确触发的一次性工具容器执行迁移，结束后退出，不是第三个常驻服务，也不要求现在安装宿主机 goose。
- 工具存在或 Docker daemon 可连接，不表示项目镜像、数据库或应用已经验证；核心版本基线见前文，不因选版创建容器或修改环境。

### 显式启动与停止顺序

1. 准备并检查运行配置，不能缺少演示密钥或可信接入方身份。
2. 启动 PostgreSQL，等待数据库就绪，不把容器正在运行等同于数据库已经可用。
3. 操作者明确触发独立迁移任务；迁移失败，不继续启动应用，不以清空数据库绕过问题。
4. 应用自身检查配置、数据库连接和所需迁移状态，通过后才接收业务请求；应用启动不偷偷执行迁移。
5. 确认应用就绪，再通过 HTTP 演示提交、查询及重放。

- Compose 的启动依赖与健康检查只帮助启动排序，不保证数据库在整个运行期间始终可用；运行中依赖故障仍按既定合同处理。
- 普通停止、重启或替换应用都保留数据库命名卷，不因重启扫描未知订单补付。
- `down -v` 会删除卷，不作为默认停止或清理步骤。确需清理时，仅针对已确认隔离的测试环境和目标处理，不触碰开发或演示数据。

### 最小就绪检查

提供 `GET /readyz`，它是运行就绪检查，不属于三个商城业务入口，不新增查单或管理能力。

| 应用可响应时的状态 | HTTP 状态码 | 最小响应 |
|--------------------|-------------|----------|
| 配置和必要依赖就绪，可以接收业务 | `200` | `{"status":"ready"}` |
| 必要依赖暂不可用，尚不能接收业务 | `503` | `{"status":"not_ready"}` |

- 无需 API key，只返回上述状态，不暴露密钥、连接信息、订单数据或原始错误；商城业务入口仍必须鉴权。
- 不读取业务订单、不调用 Mock 或发起付款，只做必要的轻量依赖检查。
- 就绪不证明所有支付场景正确，也不代表生产高可用；应用尚未监听或进程已退出时可能没有 HTTP 响应，不能据此假装就绪。

### 环境隔离与测试运行方式

- 开发、测试、演示使用不同 Compose 项目名及各自命名卷，不使用会意外跨项目共享的全局卷名，防止测试污染其他环境。
- 自动化重启验证先使用宿主机 Go 测试父进程、真实应用子进程和隔离 PostgreSQL 容器；测试数据库确需供宿主机连接时，仅绑定回环地址的测试端口。
- 同机测试控制通道采用私有目录中的 Unix domain socket，只供本次实验的可信测试与应用进程访问，不开放 TCP 控制端口；正常演示默认关闭。
- 宿主机应用子进程的验证不能冒充应用镜像已验证；镜像启动、配置和运行路径须在发布设计中单独安排证据。
- 不把 Docker socket 挂入业务容器；目录职责按前文规划，基础镜像变体与摘要仍待核实，本轮不选择测试端口分配值或可执行命令。

设计依据：[Compose 启动顺序](https://docs.docker.com/compose/how-tos/startup-order/)、[端口发布](https://docs.docker.com/engine/network/port-publishing/)、[持久卷](https://docs.docker.com/engine/storage/volumes/)。这些是设计来源，不是项目运行证据。

## 操作期限、取消与退出

### 演示默认时间预算

以下为本地 Mock 演示的初始上限，不是性能实测或生产 SLA；后续调整须记录原因，不得为让测试通过而放松幂等、结果保护或追踪边界。

| 范围 | 上限与起算规则 |
|------|----------------|
| 应用启动时等待依赖就绪 | 30秒；配置无效直接失败，不等满上限 |
| 独立迁移任务执行 | 60秒，与应用启动等待分别计时，不套用短业务事务期限 |
| HTTP 请求读取 | 5秒，包含请求头和请求体读取 |
| 支付业务主处理 | 10秒，从进入支付业务开始；必要收尾可按下文额外共享一次有限窗口 |
| 单次 Mock 调用 | 3秒，仍受外层剩余期限限制 |
| 应用数据库操作或完整短事务 | 2秒，包含取连接、等锁、SQL及提交，不给每条SQL重新计时 |
| 必要保存收尾 | 每请求额外最多一次2秒，保存、重试、读回核对及事务清理共享 |
| HTTP 响应写出期限 | 20秒，从读完请求头、进入应用处理时起算，覆盖请求体读取、处理和收尾，不是处理后另加20秒 |
| readyz 依赖检查 | 1秒，不读取业务订单或调用 Mock |

- 子操作上限还须受外层剩余时间约束；每次 SQL、保存重试或其他步骤不能重置主处理或收尾总期限。
- 主处理10秒加最多一次2秒收尾，不能宣称全部工作在10秒内完成。启动等待30秒与迁移60秒分别计时，也不表示整套环境30秒即可就绪。
- HTTP 写出期限不能代替业务取消机制；请求读取或响应传输超时，不证明付款或数据库事务已回滚。

### 取消与每请求一次的有限收尾

- 在真正进入 Mock 前再次检查取消和期限；已观察到取消或到期时，不再开始新的付款或核实调用。已经进入调用后，取消不能证明 Mock 未提交，也不能恢复付款资格。
- 收尾只处理已经取得的固定答复、超时或故障观测，以及已经发生但提交情况不明的数据库事务核对；不再查 Mock、补付或等待一个更好的结果。
- 同一请求的保存、保存重试、读回核对和事务清理共用一个最多2秒窗口，迟到答复或失败不能重开窗口；不能为无效或未鉴权请求借收尾进入订单流程。
- 该窗口可以不随客户端取消立即结束，但必须纳入应用生命周期并受退出截止约束，不产生无人管理的后台付款或无限等待。
- 客户端已断开时不能保证 `issues` 或 `error` 送达；仍须如实处理和脱敏留痕，不能声称响应已送达或追踪已经落库，也不能改写已有确认事实。

### 共享总期限的退出顺序

- 应用优雅退出最多20秒，包含停止接入、在途工作、必要收尾及资源清理；容器停止宽限为25秒，作为外层余量，不是另一个可反复领取的应用预算。
- 先置为不就绪并停止接收新请求，再让在途工作和有限收尾在各自原期限及退出截止内结束，期间保留所需数据库访问能力。
- 数据库使用者退出后关闭连接池，最后处理日志等资源；须为关闭动作预留时间，不能等满20秒才开始关池，也不能无限等待关池。
- 达到退出截止则取消剩余工作并退出，不通过新开收尾窗口延长总期限；取消、断连或强制退出都不证明数据库已经回滚。

### 普通超时与故障实验的预算区分

- 普通超时场景验证上述默认期限；测试屏障默认最多10秒，专用于可控场景，不作为正常业务延迟目标。
- 屏障场景须同步有界调整所有包含屏障的上层期限，包括相应 Mock、数据库事务、请求输出或退出预算，并在报告中记录差异，不能只拉长屏障等待自身。
- 探针或屏障自身超时不能冒充目标业务故障已命中；不能用放宽后的故障实验结果证明默认时限、性能或可靠收尾必然完成。

## 日志与验收证据留存

### 三类信息分别承担证明责任

| 信息 | 用途与边界 |
|------|------------|
| 数据库结果处理记录 | 解释订单结果、核实依据及处理决定；正常路径应有的持久化不能因已经打印日志而省略 |
| 运行日志 | 定位请求、超时、依赖及追踪故障，不证明数据库事务已经提交 |
| 验收产物 | 保留某次测试的条件、结果及证据，不以单个退出码或截图代替行为断言 |

### 白名单结构化运行日志

- 应用向标准输出写结构化 JSON 日志，时间统一 UTC。按需要记录时间、级别、事件类别、`request_id`、操作阶段、结果变化、稳定原因分类及脱敏说明。
- 只有已知且经校验的接入方、业务订单号和平台订单号才能作为关联字段；未知时省略，不补造，不将调用者未经验证的身份当成可信身份。
- 不记录密钥、`Authorization`、数据库连接串、完整请求或答复、原始 SQL 及未经处理的异常内容；框架日志和测试工具输出也不能豁免。数据库侧不启用全量 SQL 或参数打印。
- 业务结果 `FAILED` 不等于系统处理出错；日志仍须区分付款事实与本次处理故障，不把日志错误条数当付款失败数。

### 项目级容器日志轮转

- 本项目应用与数据库容器使用 Docker `local` 日志驱动，轮转选项为 `max-size=10m`、`max-file=3`；只在项目服务配置中指定，不修改宿主机 Docker 全局设置，不增加集中日志服务。
- 应用输出的 JSON 与 Docker 内部日志存储格式不是同一概念；通过 Docker 提供的日志读取能力查看，不直接操作 daemon 管理的日志文件。
- 轮转可能覆盖旧日志，移除容器也可能丢失诊断历史，不承诺永久保存或完整历史。因此容器日志不代替独立验收档案。

### 独立验收产物目录

每次验收使用独立的 `artifacts/<run_id>/`，在实现阶段加入 Git 忽略。本轮只记录路径，不创建目录或修改 `.gitignore`。

产物至少保留：

- 场景、脱敏后的命令、退出码和结论。
- 实际源码快照或镜像标识、环境、版本和预算配置；未提交源码可验证，但须记录真实快照，不能冒充干净提交，也不为制造版本标识擅自提交代码。
- 必要且脱敏的 HTTP 响应、白名单数据库状态，不导出整库或全部环境变量。
- 应用进程代次、独立调用观测和脱敏日志，使同一次实验跨应用重启仍可关联。

保留的命令、响应与日志须先过滤敏感内容；即使故障用例发现泄露，也不能为了证明泄露再次将敏感原文归档。

- 正式验收开始前建立采集，跨应用重启保持，结束时确认产物完整保存，不仅依赖可能已经轮转的容器日志。
- 采集不完整、写入失败或日志无法检索时，明确报告证据不足，不能把调用过日志函数当留存成功，也不能宣称留痕验收通过。
- 本地验收产物默认不自动删除；清理必须明确指定运行目录，不顺便清库或删除命名卷。CI 托管产物采用下文30天保留目标及平台上限约束，不与本地保留策略混同。
- 日志或采集故障不能改写已确认付款事实；日志也不能代替确认结果与最小依据的原子保存，不引入可靠审计补偿队列。

设计依据：[Docker local 日志驱动](https://docs.docker.com/engine/logging/drivers/local/)。当前没有日志配置、采集实现或实际留存验收证据。

## CI、双镜像发布与人工部署

本节只记录已确认的发布设计，不创建或触发工作流，也不表示仓库、镜像包、访问权限或发布产物已经存在。代码检查、镜像发布与本地部署分别承担责任，不以一次 CI 绿灯自动批准上线。

### 自动检查与发布分权

- PR 和默认分支更新时，由 GitHub Actions 执行格式、静态检查、构建、业务测试、真实 PostgreSQL 与 HTTP 集成测试，以及并发和真实进程重启验证；使用隔离环境与模拟数据，不依赖真实业务密钥。
- 普通检查只授予必要的源码读取权限，不向 GHCR 上传镜像，不因来自同仓库就给 PR 检查写包权限；不使用 `pull_request_target` 检出并执行不可信 PR 代码。
- 发布仅由 `workflow_dispatch` 人工触发，且只允许默认分支的受信提交。手动入口不是任意 ref 的发布授权，必须限制并核实本次选择的来源。
- 一轮发布固定同一个源码提交号，对该提交完成检查，不借用另一提交或 PR 合并快照的绿灯；不能随默认分支后续移动改变构建输入。
- 普通检查的 `GITHUB_TOKEN` 仅需 `contents: read`；只有上传镜像的 job 另授 `packages: write`，其余权限保持最小。基础 GHCR 上传不额外申请 `id-token` 或证明签发权限。

### 同一产物、双镜像配对与验证关卡

发布顺序为：固定源码提交并完成检查 → 各构建一次应用镜像与迁移工具镜像 → 在隔离环境验收这对实际镜像 → 推送同一份产物 → 按最终远端摘要拉回复核 → 记录为可用发布。

- 应用镜像与迁移工具镜像分开打包；迁移镜像包含精确选定的 goose 及该源码修订的 SQL。两者来自同一源码修订，作为一组验收、发布和选用，不任意混配应用、工具或 SQL。
- 实际镜像验证至少覆盖真实迁移、正常启动、关键 HTTP 闭环，以及保留数据库的重启与不重付；付款调用与交易效果仍分别取证。故障控制仅在可信测试模式启用，正常配置不依赖测试控制器，不把宿主机二进制测试冒充镜像验收。
- 底层业务、数据库与 HTTP 测试继续承担各自主证据，不要求在镜像内机械重复全部单元测试；发布前完整验收范围仍包含既定17个业务场景及新增 HTTP 边界，不能以镜像冒烟替代。
- 首期只构建和验证 `linux/amd64`，不新增多架构发布；一个平台通过不代表其他平台通过。
- 通过验收后推送原产物，不在上传或部署阶段重新构建；记录最终 registry manifest digest，按摘要拉回核对内容并验证运行路径。转换产物、重建或改变平台、manifest 后，不能直接沿用旧身份与验收结论。
- 推送不等于发布验收通过。即使已经上传，拉回复核失败或证据不完整也只是未通过的候选，不能标记可用或部署。

### 标识、发布记录与外部前提

| 标识 | 用途与限制 |
|------|------------|
| 源码提交号 | 定位构建输入，不是可拉取镜像内容的摘要 |
| 本地镜像 ID | 在本机识别镜像，不能当作 registry manifest digest 使用 |
| 仓库摘要 `@sha256:…` | 锁定从仓库拉取的具体内容；不单独证明安全、所有平台通过或迁移可逆 |

- 标签只用于方便查找，可能移动，不以 `latest` 或源码提交标签代替最终摘要；发布记录包含源码提交号、平台、应用与迁移两个最终摘要及对应验收报告。
- 首次真实发布前确认实际仓库、GHCR 包与仓库关联、上传及拉取权限和可见性；不自动公开镜像，也不假设公开源码会使包自动公开。缺少必要访问权限时停止，不擅自创建凭据或放宽访问。
- CI 脱敏验收产物以30天为保留目标，遵守仓库、组织或企业上限；实际不足时明确记录，不宣称已保存30天或永久归档。保留内容仍遵循前述白名单与采集完整性要求。

### 人工部署与失败边界

- 本地由操作者明确选择已验证的一对镜像摘要，显式执行对应迁移后再启动应用；不自动部署，不在部署时重新构建，不改变既定数据库持久化与付款资格规则。
- 迁移或启动失败时停止并诊断，不自动执行降级迁移、不删卷或清库恢复。切回旧应用前须先确认当前数据库兼容，不能将换镜像当作数据库已经回退。
- 核心工具版本按前文基线，具体 workflow、命令及真实外部资源配置留待对应授权；本轮不认证、不构建或拉取镜像、不上传、不部署、不创建 GitHub Release，也不提交或推送。

设计依据：[Actions 触发器](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)、[GITHUB_TOKEN 权限](https://docs.github.com/en/actions/security-for-github-actions/security-guides/automatic-token-authentication)、[GHCR](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)、[Actions 产物保留](https://docs.github.com/en/actions/using-workflows/storing-workflow-data-as-artifacts)。这些是设计来源，不是执行证据。

## 验证分层与证据策略

本节记录第 4 阶段前两轮已确认的验证方向与夹具方案，不是测试执行报告。先为关键承诺选择能够建立或推翻它的证据，不以覆盖率数字、脚本存在或文档检查通过代替行为验收。

### 四层验证与主证据归属

| 验证层 | 主要负责证明的内容 | 不能替代的证据 |
|--------|--------------------|----------------|
| 业务规则测试 | 金额边界、重复与冲突判断、结果接受及保护规则；使用可控依赖验证业务分支 | 真实 PostgreSQL 的约束、锁与并发语义 |
| 真实 PostgreSQL 集成测试 | 唯一键、登记及结果保存短事务、行锁、确认与依据原子保存、同次观测保存重试；在隔离测试库验证真实迁移和 SQL | HTTP 解析、鉴权或响应合同 |
| HTTP 集成测试 | 通过实际 Gin 路由验证请求、响应及真实存储效果；关键闭环连接真实 PostgreSQL 与内部 Mock，流式大小限制覆盖实际 HTTP 连接 | 独立进程或容器的真实重启 |
| 真实应用重启验证 | 保留数据库，实际停止并启动应用，查询和重放成功、失败、未知三类已登记订单，检查身份、事实及不重付 | 磁盘损坏恢复、生产高可用或真实资金安全 |

每项关键承诺由对应主验证层负责建立或推翻，必要时补充相邻边界检查；不要求所有场景在每一层重复运行。

### 五组关键风险覆盖

| 风险组 | 最低需要证明的事实 | 主要证据归属 |
|--------|--------------------|--------------|
| 无效请求没有业务效果 | 输入及鉴权拒绝不新增订单、不发起付款；鉴权失败不读取订单。覆盖400、401、413、415等合同分支，不只检查状态码 | HTTP 集成测试，结合访问、付款调用和数据库状态观察 |
| 重复、并发与冲突不重付 | 复用同一订单，不改原始事实；分别核对付款调用次数与 Mock 交易事实或效果；失败后重放仍不重付 | 真实数据库并发测试及关键 HTTP 集成路径 |
| 未知核实与确认结果保护 | 覆盖答复丢失、平台无记录、Mock 无匹配、查询故障与错配；匹配依据才确认，已有确认结果不降级，不通过核实重付 | 业务规则、真实数据库与 HTTP 边界的对应主测试 |
| 结果保存与追踪故障 | 新确认与依据不出现半套保存；提交不明会核对；追踪失败明确报告并留受控脱敏记录，不冒充完整成功 | 真实数据库故障测试及 HTTP 响应、日志证据 |
| 真实重启与已登记事实保留 | 三类订单重启后仍保持原标识、金额、币种和关联；相同意图重放不重付，未知不因重启自动确认 | 独立进程重启测试及跨重启保存的证据 |

- 已批准规格中的17个验收场景仍须覆盖，并与16条功能要求、11条成功标准核对；接口设计新增的严格输入与 HTTP 边界也须安排相应测试。
- 并发请求可以在各自处理时刻返回不同状态快照，但必须关联同一订单，后续核实所得结果一致；不要求永久冻结首次响应。
- 一个 Mock 交易行不能证明只有一次付款调用；Mock 可能挡住重复调用。付款发起边界必须独立观测，不能用交易或处理记录条数代替。
- `2xx` 不能证明付款成功、处理无异常或追踪完整，必须同时检查 `payment.result`、`issues` 和实际保存情况。追踪故障处理符合预期，不等于追踪完整性验收已经通过。
- 重新创建 Go 对象不算应用重启。必须真实停止、启动应用，并留存前后证据；内存计数重置后不能推算跨重启总付款调用数。

### 测试夹具、故障控制与独立观测

**生命周期与隔离**：Go 测试父进程负责启动、暂停和重启真实应用子进程，父进程自身跨应用重启保持，数据库也保留。夹具代码长期保留在测试工具中，观察器运行实例随实验结束退出，不成为第三个常驻业务服务。

- 少量同步观测、屏障与故障注入接缝仅由可信测试准备和配置启用，正常业务运行默认关闭，不依赖测试父进程。
- 不新增商户控制路径，不允许商城通过业务请求指定 Mock 场景，不新增业务计数表、可靠审计队列或补偿系统；同机进程间通道采用前述私有 Unix domain socket。
- 场景互相隔离，在明确位置暂停或释放，不以随意等待猜测并发时序。屏障默认上限和关联操作预算按前述期限策略处理。

**US1真实失败夹具补充批准（2026-11-09）**：用户已明确选择在既有私有test-control上增加最小的Mock结果指令，而非第二个fixture二进制。仅在可信testmode的付款入口使用，一次性绑定本次实验、进程代次、实际订单及事件序号；只允许显式SUCCEEDED/FAILED，不覆盖已经保存的渠道事实。未消费指令、身份/序号错配、超时或封口异常必须判证据不完整，不能退回默认成功或冒充业务失败。正常testmode关闭路径仍显式默认成功，不新增业务字段、HTTP控制接口或普通环境开关，不提前实现T060完整故障矩阵。协议扩展与实际失败POST/PG/重启闭环在批准时尚待实现和独立验收；包内私有generator测试不能替代这项证据。最终实现与本机验收见 quickstart 0.2。

技术封口合同：Ack写出只证明释放指令；既有MockCommitted事件须携带原付款call序号和渠道实际提交结果，与本次完整身份及pending指令匹配后才证明消费。不得回显预期值或用复用旧交易冒充新提交；未闭合时Seal不得成功。保留既有同seq传输重试/冻结Ack重放，不重复计数或消费；Hold解锁后等待，绝对2秒上限同时服从Mock与请求剩余预算。批准时此合同尚未接线；最终实现与本机验收见 quickstart 0.2，最终验收仍须另查原始PG事实。

| 受控位置 | 验证目标与事实边界 |
|----------|--------------------|
| 平台已登记但尚未付款 | 在此中断并真实重启后，不能读取未知订单重新取得付款资格或补付 |
| Mock 已提交但答复尚未送达 | 丢失答复可使平台暂时未知，后续核实必须仍关联原交易；Mock 已保存的成功或明确失败事实不改写 |
| 平台保存确认结果与依据期间 | 实际 SQL 失败或提交答复丢失后，核对真实 PostgreSQL 中的订单和处理记录，不允许半套新确认 |

- 查询故障、暂不可见和错配只作用于本次答复，不通过开关改写已有 Mock 交易事实，查询也不能产生付款效果。
- SQL 失败场景须实际执行 SQL 并检查事务事实，不只伪造存储错误。真实提交后由测试接缝隐藏成功答复，可验证受控答复丢失处理，但不等于已经验证真实网络断链。

**付款调用观测**：目标是在 Mock 付款入口、防重及实际效果之前独立观测每一次进入，包括被 Mock 防重挡住的重复调用。

- 每次独立调用使用独立观测身份，并保留可关联实验、应用进程代次与订单的记录；不能按订单或外层请求号合并调用。
- 同一事件的传输重试可以复用身份并去重；真正第二次调用必须另记。查询单独计数，不混入付款次数。
- 测试父进程跨应用重启累计观测；观察器只负责记录，不能以“每单只放行一次”替业务防重，否则会掩盖缺陷。

**证据不足时不通过**：同步观测仍可能有交付不明，不能仅将收到确认的事件数宣称为全部真实调用数。只有受控窗口、调用边界和前后证据闭合，才报告精确次数。

- 观察器离线或重启、等待超时、应用在事件交付期间意外中断等留下缺口时，将场景判为不确定或失败，均不算验收通过，不能按零调用通过。
- 不把探针问题伪装成 Mock 明确付款失败；探针阻塞造成的超时不能冒充目标故障已命中，必须区分夹具故障和被测行为。
- 该方案证明可重复的受控故障窗口，不承诺任意崩溃或断电下无缺口审计、生产性能或端到端恰好一次，也不新增自动补付路径。

### 执行记录、隔离与验证预算

- 后续每次实际执行至少记录场景、命令、退出码、代码或镜像版本，以及相关响应、数据库状态和脱敏记录，让结论可以复查；当前没有这些功能测试证据。
- 测试、开发和演示环境隔离，测试从可复现状态开始，清理只在明确隔离的测试环境执行，不触碰其他环境数据。
- 每次改动按影响范围选择检查，发布前执行完整验收；相关代码、输入、环境或状态变化后，失效的旧证据必须重新验证。
- 测试夹具、本地通道、故障控制、独立观测、期限及留证策略已记录；实际执行准备仍待完善，当前不把证据路径视为已经实现或可直接执行。
- CI、发布、核心版本、目录及运行指南流程已按前文评审；基础镜像与 CI 引用须在实现准备时核实，配置、真实命令和可执行步骤尚未实现，本轮不生成测试代码、夹具、服务配置或新接口。
